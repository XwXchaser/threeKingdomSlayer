#### 4.2 BUG 1：无限补齐（Z 轴方向搞反）

| 字段 | 内容 |
|------|------|
| **类型** | fix |
| **范围** | `Enemy.cs` |
| **描述** | 击杀敌人后，后方敌人持续打印 Moving 日志，progress 值递增但永远无法到达 1，无限循环 |
| **详细说明** | **根因**：Z 轴方向搞反。在 Unity 中 -Z 轴是前进方向（朝向玩家），+Z 轴是后退方向（远离玩家）。旧公式 `zPos = -(rowIndex * rowSpacing)` 让 `rowIndex=0` 在 `z=0`，但正确的应该是 `rowIndex=0`（最前排）在 `z=-10`（最靠近玩家）。因为 Z 轴方向反了，`Lerp` 从旧排向新排移动时方向错误，敌人永远无法到达目标位置。**修复**：新增 `GetRowZ()` 辅助方法，公式改为 `(maxVisibleRows - 1 - rowIndex) * (-rowSpacing) + offsetZ`。`rowIndex=0` → `z=-10`，`rowIndex=4` → `z=0`，前进方向为 -Z |

#### 4.3 BUG 2：梯形向内聚拢（isRushMoving 机制引入）

| 字段 | 内容 |
|------|------|
| **类型** | fix |
| **范围** | `Enemy.cs` / `Column.cs` / `ColumnManager.cs` |
| **描述** | 击杀敌人后，后方敌人向中间聚拢（X 轴偏移变化），看起来像梯形向内收缩 |
| **详细说明** | **根因**：引入 `isRushMoving`/`StartRushMoving()` 机制后，`Column.RemoveEnemy()` 先调用 `StartRushMoving()`（保存旧 `rowIndex` 到 `rushStartRow`），再调用 `SetRowIndex()` 更新 `rowIndex`。`UpdateWorldPosition()` 中 Z 轴使用 `rushStartRow`（旧排位置），但 X 轴使用 `rowIndex`（新排位置），X 轴和 Z 轴不同步。**修复**：移除 `isRushMoving`/`StartRushMoving()` 机制，恢复到上一版本的 `ResetMovementState()` + `StartMoving()` 逻辑。`SetRowIndex()` 先更新 `rowIndex`，`UpdateWorldPosition()` 中 X 轴和 Z 轴都使用更新后的 `rowIndex`，完全同步 |

#### 4.4 BUG 3：无限尝试向前补齐（isRushMoving 机制引入）

| 字段 | 内容 |
|------|------|
| **类型** | fix |
| **范围** | `Enemy.cs` |
| **描述** | 击杀敌人后，后方敌人无限尝试向前补齐，日志显示反复触发补齐移动 |
| **详细说明** | **根因**：补齐移动完成后 `state=Idle`，`StartMoving()` 被调用导致常规移动开始，常规移动完成后 `rowIndex--` 触发 `UpdateEnemyRow()`，再次补齐移动，无限循环。**修复**：`UpdateMovement()` 中移动完成后不再调用 `StartMoving()`，避免无限循环 |

### 2. BUG 修复：秒杀整列后补齐异常

#### 2.1 问题描述

| 字段 | 内容 |
|------|------|
| **类型** | fix |
| **范围** | `Column.cs` / `ColumnManager.cs` |
| **描述** | 秒杀整列敌人时，存活敌人瞬移到第二排然后开始补齐，而非从后排逐个前进 |
| **详细说明** | 横扫/范围攻击同时击杀多排敌人时，死亡协程（`FlashThenRelease`，0.15s 闪白 + 0.3s 缩放）同时完成，`OnDeath` 事件几乎同时触发。后续每个死亡敌人的 `RemoveEnemy()` 会重新调用 `SetRowIndex(i+1)`，导致已设置好链式补齐的存活敌人排索引被覆盖（瞬移），且链式补齐因 Dead 状态的敌人无法启动 |

#### 2.2 根因分析

| 字段 | 内容 |
|------|------|
| **范围** | `Column.RemoveEnemy()` |
| **详细说明** | 以击杀第0、1排为例：① enemy0 死亡 → `RemoveEnemy(enemy0)` 正确设置 enemy1/2/3/4 的链式补齐，但 `firstToMove = enemy1` 因 `state == EnemyState.Dead`（enemy1 也同时死亡）导致 `TryStartRushMove()` 失败，链式补齐永久中断。② enemy1 死亡 → `RemoveEnemy(enemy1)` 重新处理存活敌人，`SetRowIndex(1)` 让 enemy2 从 row=2 瞬移到 row=1，`SetRowIndex(2)` 让 enemy3 从 row=3 瞬移到 row=2，然后 enemy2 从 row=1 移动到 row=0。视觉效果：整列敌人瞬移到"第二排"后开始补齐 |

#### 2.3 修复方案

| 字段 | 内容 |
|------|------|
| **范围** | `Column.cs:70-130` / `ColumnManager.cs:120-178` |
| **详细说明** | 在 `Column.RemoveEnemy()` 和 `ColumnManager.UpdateEnemyRow()` 中，设置链式补齐前先扫描列表中所有 `state == EnemyState.Dead` 的敌人并将其从列表移除（它们稍后由各自 `OnDeath` 事件处理）。然后将存活敌人紧凑排列、重新设置正确的 `SetRowIndex(aliveCount + 1)` 和 `targetRow = aliveCount`。这样链式补齐只对存活敌人执行，`TryStartRushMove()` 不会因 Dead 状态失败，存活敌人的位置也不会被后续 RemoveEnemy 重新覆盖导致瞬移 |

#### 2.4 修改文件

| 文件 | 修改内容 |
|------|----------|
| `Column.cs` | `RemoveEnemy()`：移除目标敌人后，过滤 Dead 敌人，补偿排列存活敌人，`RemoveRange` 清除空洞，从 `enemies[0]` 启动链式补齐 |
| `ColumnManager.cs` | `UpdateEnemyRow()`：重排列后，从 `currentIndex` 开始扫描，跳过 Dead 敌人，紧凑排列存活敌人，`RemoveRange` 清除空洞 |

#### 2.5 v2 修复：移除 SetRowIndex 瞬移（根因修复）

| 字段 | 内容 |
|------|------|
| **类型** | fix |
| **范围** | `Column.cs` / `ColumnManager.cs` |
| **描述** | v1 修复（过滤 Dead 敌人）未能解决瞬移问题，因为 `SetRowIndex()` 本身是瞬移的根因。v2 修复：完全移除 `SetRowIndex()` 调用，保持敌人当前 `rowIndex`，利用 `targetRow` 控制多步补齐 |
| **详细说明** | **问题复现**：v1 修复后用户反馈"BUG依旧存在，横扫秒杀两排敌人，第三排和后续排的敌人会瞬移到第二排然后再开始补齐"。**v1 修复的局限**：过滤 Dead 敌人解决了链式补齐被 Dead 状态中断的问题，但 `SetRowIndex(aliveCount + 1)` 仍然立即调用 `UpdateWorldPosition()`，将敌人从原始位置（如 row=2）瞬时跳转到目标位置（row=1），这就是用户看到的"瞬移"。**v2 修复方案**：不再调用 `SetRowIndex()`，敌人保持当前 `rowIndex`，只设置 `targetRow` 和 `pendingRushMove`。`UpdateMovement()` 中移动完成后检查 `rowIndex <= targetRow`，若未到达则延迟后继续移动（多步补齐），从当前位置一步步前进到目标位置，完全无瞬移。**示例流程**：击杀 row 0, 1 后，enemy2(row=2) → targetRow=0，移动 row=2→1→0（两步补齐）；enemy3(row=3) → targetRow=1，移动 row=3→2→1；enemy4(row=4) → targetRow=2，移动 row=4→3→2。所有敌人从各自当前位置逐步前进，无任何跳转 |

### 5. BUG 修复：attackRange 无效

#### 5.1 问题描述

| 字段 | 内容 |
|------|------|
| **类型** | fix |
| **范围** | `Enemy.cs` |
| **描述** | 无论 `EnemyConfig.attackRange` 设置为多少，敌人都只有移动到最前排（rowIndex=0）才会开始攻击玩家 |
| **详细说明** | `Initialize()` 和 `StartMoving()` 中硬编码了 `rowIndex <= 0` 作为进入攻击状态的判断条件，完全忽略了 `config.attackRange` 值。`UpdateMovement()` 中虽有正确的 `attackRange` 判断，但 `StartMoving()` 在移动开始前就拦截了——敌人若已在攻击范围内（如 attackRange=3, rowIndex=2），`TryStartRushMove()` → `StartMoving()` 发现 `rowIndex=2 > 0`，继续移动而非攻击。同时，初始生成在攻击范围内的敌人（如 attackRange=3, rowIndex=2）因 `Initialize()` 中 `rowIndex <= 0` 为 false，保持 Idle 状态永不攻击。 |

#### 5.2 修复方案

| 字段 | 内容 |
|------|------|
| **范围** | `Enemy.cs:Initialize()` 第 139-141 行、`StartMoving()` 第 232-234 行 |
| **详细说明** | 两处均改为 `int attackRange = config != null ? (int)Mathf.Max(1, config.attackRange) : 1; if (rowIndex < attackRange) { StartAttacking(); }`。`Mathf.Max(1, ...)` 确保 `attackRange=0` 时强制为 1（仅在 rowIndex=0 攻击），与 `UpdateMovement()` 中的计算方式保持一致 |
