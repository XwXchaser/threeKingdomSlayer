# 动作游戏手感与输入缓冲（设计提案，2026-11-05）

> **状态：提案，待用户拍板。** 本文是 `design/combo-move-state-machine.md` §5（输入模型 A / B）与 §14（坑点）的深化与修正，也是 2026-11-05 五条手感反馈的落点依据。
> 术语沿用 `combo-move-state-machine.md` §1；不改的动作/数值/表现规则仍以那份文档为准。

---

## 0. TL;DR

1. **"不跟手"通常不是延迟大，而是"输入被丢弃"和"承诺点太晚"。** 本项目两条都占。
2. **动作游戏的预输入 = 三件套**：**记住输入** + **在最早可执行帧兑现** + **让玩家看见它被记住了**。缺任何一件，玩家都会觉得"游戏没理我"。
3. 本项目现存的缓冲是**半套**：单槽、只对"有匹配边的手势"生效、招式一结束就清空、动作锁吃输入是静默丢弃。
4. **关键发现**：当年把"按下即出轻攻击"撤回的理由是「与起手即蓄力冲突」（`combo-move-state-machine.md` §11.6）。而 **2026-11-05 的"中立态彻底不许蓄力"已经把那个冲突源删掉了** → 方案可以用新语义复活，不需要新发明。
5. 目标（可测）：**按下 → 动画启动 ≤ 1 帧**；**输入 → 兑现 ≤ 0.25s**；**合法输入丢弃率 = 0**。

## 1. 动作游戏的"预输入"到底是什么

"预输入"在玩家嘴里是一个词，在实现里是**五个可分离的机制**。混着做必然顾此失彼，所以先拆开。

| 机制 | 定义 | 典型参数 | 本项目对应 |
|---|---|---|---|
| **输入缓冲（input buffer）** | 玩家在"现在不能出招"的帧按下的输入被**记住**，在**最早能出招的那一帧**自动兑现 | 6–12 帧（0.1–0.2s）；手游长动作可到 0.25–0.3s | 有，但只覆盖"有边手势 + 窗口开启前"，且招式结束即清 |
| **取消窗口（cancel window）** | 招式收尾里的一段区间，在这段里**可以打断收尾**接下一招 | 通常从**伤害判定结束**开始，持续到收尾结束 | **没有独立概念**；只有"接续窗口"，且它的起点是手填的 0.65 |
| **命中取消（hit-cancel）** | 只在**打中**时开放取消窗口；空挥不开放 | 命中后立刻可取消 | 无（现在空挥与命中都只是"等窗口"） |
| **土狼时间（coyote time）** | 离开可动状态的**短暂宽限**，让输入仍然有效 | 0.1s（平台跳跃的类比） | 无对应；本项目对应物是"动作锁刚结束的那几帧" |
| **承诺点（commit point）** | 玩家按下到"这一下算数"之间的分界 | 按钮游戏 = 按下即承诺；手势游戏 = 需要一个判定规则 | **现在承诺点在"抬手"** → 轻攻击固有延迟 80–150ms |

### 1.1 为什么缓冲必须配"可见反馈"

缓冲的本质是**替玩家记住一次意图**。如果玩家按下去看不到任何反应，他会以为游戏没收到 → 于是再按一次 → 反而多打一招，或者以为输入不稳定。

所以成熟做法是三件一起上：

1. **记住**（内部）
2. **兑现**（在最早可执行帧）
3. **反馈**（玩家看得见"我按下的那一下被存着了"）—— 常见表现：招式图标高亮、枪口预亮、手势提示圈闪一下

本项目第 3 条**完全没有**，这是"输入被吞"体感最强的放大器。

### 1.2 四个经典反模式（本项目全中）

| 反模式 | 后果 | 本项目现状 |
|---|---|---|
| 静默丢输入 | 玩家认为是 bug，不是手感问题 | `AttackSystem.cs:426` 动作锁期间 `return false`，无任何提示 |
| 缓冲无上限 | 连点堆积成"搓招队列"，行为不可预测 | 现在无缓冲所以没这问题；加缓冲后必须"只保留最近一条"（`combo-move-state-machine.md` §14 坑点 12 已预警） |
| 动作锁与视觉不同步 | 玩家看到枪还没收，输入却已经能出 → 武器闪断（违反 §19 动作准则） | 坑点 1 已记录；卡肉期间**动作锁继续走、招式时钟冻结**（本文 §2 表） |
| 空挥与命中惩罚不一致 | 节奏忽快忽慢，"有时反应快有时慢" | 现在只有命中才设动作锁；空挥整段招式不开（本文 §2 轴 6） |

## 2. 本项目现状体检（2026-11-05 实测）

> 实测方式：`MoveTable_Zhangfei.asset` 与 `Hero_Zhangfei.asset` 经 Unity 读出；场景实例值经 `FindObjectOfType` 读出；代码行号对应 HEAD `8b9a3438` 附近。

### 2.1 六轴体检表

| 轴 | 现状（实测） | 玩家感知 | 目标 |
|---|---|---|---|
| **轴 1 判定时机** | 点按在**抬手**才结算（`InputManager.Pointer.cs` 鼠标抬起 → `ProcessGesture`） | 轻攻击固有延迟 80–150ms | 按下即承诺，≤1 帧 |
| **轴 2 蓄力门** | `chargeLevelTimes = [0.3, 0.6, 1.0]`；场景 `minChargeTime = 1`（但一级门槛实际取 0.3）；**2026-11-05 起中立态不许蓄力**（`IsChargeAllowed()` = `comboChargeActive`） | 中立态按住 = 什么都不发生 | 已基本到位（见 §3） |
| **轴 3 输入缓冲** | 单槽 `_hasBuffered`；只对**有匹配边的手势**缓存（`CanResolve` 为假直接拒绝）；窗口开启前才缓存；`BeginMove`/`ExitToNeutral` 都清空；动作锁吃输入静默丢弃 | "我点了，它没动" | 只保留最近一条 + 有效期 + 跨招式兑现 + 可见反馈 |
| **轴 4 取消窗口** | **没有独立取消窗口**。只有"接续窗口"，Jab1 = `[0.65, 1.00]` → 实际 **0.2925s** 才打开；而伤害判定在 12%–48%（0.054–0.216s）→ **窗口比命中晚 0.08–0.24s** | 连招第二下总是"等一下" | 取消窗口锚到**伤害窗口结束**，与攻速自动同步 |
| **轴 5 动作锁 vs 招式时钟** | 卡肉（Light 0.045 / Standard 0.09 / Heavy 0.14）期间：状态机时钟**冻结**（`PlayerMoveStateMachine.Update` 早退），动作锁**继续走**（`AttackSystem.Update` 用 `Time.deltaTime` 递减） | 命中后节奏错位；有时看着枪没收却已经能出下一招 | 两者统一（建议都随卡肉冻结） |
| **轴 6 空挥一致性** | 空挥 → `TryExecuteAttack` 返回 false → **动作锁不设、招式节点不开** | 打空 = 无限快打，打中 = 被锁 0.45s | 空挥给一个短锁（或统一为命中才推进段位） |

### 2.2 延迟预算（按下 → 玩家看到结果）

| 环节 | 现状 | 目标 |
|---|---|---|
| 手指按下 → 承诺 | 玩家按住时长（80–150ms） | **0–16ms**（按下即承诺） |
| 承诺 → 动画起手 | 0（同一帧起手） | 0 |
| 起手 → 伤害判定 | 0.054–0.216s（Jab1，比例随攻速缩放） | 不变（这是**动作设计**，不是延迟） |
| 判定 → 可接下一招 | 0.2925s（Jab1 窗口起点） | **伤害判定结束时**（≈0.216s） |
| 输入被丢弃 | 静默丢弃，无上限 | **0 丢弃**；最迟 0.25s 内兑现 |

> 注意"起手 → 伤害判定"这一段**不该被压缩**：它是挥枪的物理过程，压掉会让打击感变轻（`design/combat-hit-feedback-direction.md` 的分级原则）。要压的是**承诺点**和**等待窗口**。

## 3. 关键结论：当年撤回"按下即出"的原因已经消失

`combo-move-state-machine.md` §11.6 记着：

> 轴 1（按下即出轻攻击 + 起手改写）**已撤回**：它与「起手即蓄力」冲突。

当时的冲突是：**中立态按住 = 站桩蓄力（穿刺）**。如果按下就出轻攻击，那么"想蓄力"的人会先打出一记轻攻击（甚至已经命中）→ 蓄力被偷。

而 2026-11-05 的三个提交把这件事做掉了：

| 提交 | 效果 |
|---|---|
| `6c047035` | 暂时停用「无前置的纯蓄力横扫」 |
| `e7888a13` | 滑向的蓄力必须有前置招式 |
| `2234ed95` | **中立态彻底不许蓄力**（`IsChargeAllowed()` 只认 `comboChargeActive`） |

→ 现在**中立态按住什么都不发生**，所以"按下即出轻攻击"与"起手即蓄力"**不再冲突**。
→ 而且预留接口**都还在**：`AttackSystem.TryCancelLightAttackStartup()`、`StabSweepEffect.TryCancelBeforeHit()`、`PlayerMoveStateMachine.NotifyExternalReset()` —— 目前**零调用点**（§11.7 明确说"作为后续接续取消的预留接口保留"）。

**结论**：轴 1 可以复活，且工程脚手架已备好；需要重新定义的是**承诺点规则**（§4.2），而不是从零设计。

## 4. 目标手感模型（规范）

### 4.1 输入的五段式

```
识别(gesture) → 承诺(commit) → 起手(windup) → 判定(hit) → 收尾(recovery)
                  ↑ 新增                    ↑ 已有      ↑ 已有
```

- **识别**：手势是什么（点/滑/长按）。**允许有歧义，靠承诺点规则消歧。**
- **承诺**：从这一帧起，玩家的这一次输入算数（可能改写、可能兑现）。
- **起手**：武器进画、蓄势。**起手可以持续到判定**，期间仍允许改写。
- **判定**：伤害结算。
- **收尾**：不可打断段（除非在取消窗口内）。

### 4.2 承诺点规则（本项目的具体口径）

| 输入 | 承诺点 | 规则 |
|---|---|---|
| **点按（轻攻击）** | **按下那一帧** | 立刻进入 Jab1 的起手；判定在命中帧结算 |
| 点按后**移动超过阈值**且**在判定之前** | 移动那一帧 | **改写**为手势招式（`TryCancelLightAttackStartup` → 取消起手 → 出手势招）；**不留下误伤的轻攻击** |
| 点按后**一直按住** | — | 中立态按住无意义（蓄力已禁）→ 轻攻击照常在判定帧结算 |
| **连段窗口内按住** | 按住那一帧 | 进入**连段蓄力**（`comboChargeActive`）→ 松手/上划释放派生招 |
| **滑动** | 识别到方向的那一帧 | 未蓄力的滑动 = 即时招式（Slash / Sweep 等） |

**风险与对策**：改写窗口 ≈ 起手段（0.054s 起手 + 刺出 0.126s）→ 约 **0.05–0.18s**。若玩家划得慢，滑动识别（`swipeThreshold=50px`、`minSwipeSpeed=180px/s`、`maxSwipeDuration=0.25s`）可能晚于判定 → 会留下"一记轻攻击 + 一记手势招"。
**对策**：把轻攻击的**判定帧**从 12% 后移到 ~20%（0.09s），给改写留出可用的窗口；这 0.036s 的位移代价远小于"多打一记"的困惑。**（待实机调参）**

### 4.3 输入缓冲规范

| 项 | 规定 |
|---|---|
| 槽位 | **只保留最近一条**（新的覆盖旧的）—— `combo-move-state-machine.md` §14 坑点 12 的既定策略 |
| 有效期 | **0.25s**（可配）。到期即丢，并**记一次丢弃计数**（进埋点） |
| 缓存范围 | 任何**攻击类手势**（点/斜滑/横滑/竖滑），**不再要求"有匹配边"** → 这是"跨招式预输入"的关键 |
| **不缓存** | 蓄力手势（`chargeLevel >= 1`）、防御键、UI 点击、QTE 输入、教学闸门拒绝的手势 |
| 消费点（优先级） | ① 招式进行中且落在**接续窗口** → 立刻接续；② 招式结束回到中立 → 按中立入口执行；③ 命中取消窗口开启 → 立刻取消收尾接上 |
| 过期策略 | 静默丢弃，但**必须有反馈**（见 §4.6）与计数 |
| 卡肉交互 | 招式时钟在卡肉期间冻结 → 缓冲**跟着等**，卡肉结束那帧兑现（这正是"命中取消"最爽的那一下） |

### 4.4 取消窗口规范（新增概念）

现状把"能不能接下一招"和"什么时候能接"揉成一个"接续窗口"。建议拆成三层：

| 层 | 含义 | 锚点 |
|---|---|---|
| **接续窗口** | 某个**特定后继**（图上的边）可用的区间 | 沿用现状（配置化，逐招式微调） |
| **取消窗口** | 本招**可以被打断收尾**的区间 | **锚到伤害判定结束**（不是手填 0.65）→ 攻速变化时自动跟随 |
| **命中取消** | 取消窗口**只在打中时开放**；空挥不开放 | 打中 → 可取消；空挥 → 走完收尾 |

**为什么锚到判定结束**：这是唯一有因果关系的锚点（"我的枪已经打到了，所以可以收枪接下一招"），也天然满足 §19 武器连续性准则（不会在武器还没到位时把它切掉）。
**为什么加命中取消**：空挥也能取消 → 玩家会无脑乱按；命中才可取消 → 奖励"打中"，同时让空挥有重量（这正是"手感"里"沉"的那一半）。

> ⚠️ **与既有实测的冲突**：`combo-move-state-machine.md` §11.8 记着"首版曾设为 0.35~0.95，实测『下一段出得太快』，后移到 0.65~0.95"。那次是在**旧模型**（每次输入都要抬手）下测的，且取消与"接续"是同一件事。**建议不要照抄 0.35 或 0.65**，而是按本节拆成"取消窗口（锚判定结束）+ 接续窗口（逐招调）"，并用 §5 的指标重测。

### 4.5 卡肉与缓冲/取消的顺序（明确写死）

1. 命中 → 卡肉开始（0.045 / 0.09 / 0.14s）
2. 卡肉期间：**招式时钟冻结**、**动作锁冻结**（**这一条要改**：现在是动作锁继续走）、**缓冲保留**
3. 卡肉结束 → 取消窗口若已开放 → **同帧兑现缓冲**（"命中即取消"的爽点）
4. 未兑现的缓冲继续等，直到 0.25s 过期

### 4.6 反馈规范（缓冲/承诺的可见反馈）

| 事件 | 反馈（可实现的） | 依赖 |
|---|---|---|
| 输入被缓冲 | 枪口/手势指示圈闪一次；或招式图标短暂高亮 | 复用现有 `AttackTapIndicator` / `ChargeIndicatorController`，**尽量不新增美术** |
| 输入被兑现 | 现有起手表现即是 | — |
| 输入过期（丢弃） | **建议给一个极轻的负反馈**（例如指示圈闪红一下），告诉玩家"这次没赶上" | 需一点美术/着色 |
| 按下即承诺 | 起手表现提前 → 本身就是反馈 | — |

> 第一版可以只做"缓冲中"的一个轻反馈，**丢弃反馈可选**。

### 4.7 教学闸门与缓冲的互斥（必须写进实现）

教学用手势闸门（`TutorialAttackGate` / `tutorialGestureTarget`）会拒绝非目标手势。缓冲若跨过教学拍边界执行，会打出"教学没教过的招"。

规则：
1. **被闸门拒绝的手势不进缓冲**（教学拍期间一律不进）。
2. **教学拍切换时清空缓冲**（`combo-move-state-machine.md` §13 已列"状态复位点"）。
3. 教学拍内被缓冲的手势在拍结束前兑现 —— 现有 `holdWait`（驻留）机制已经解决"刚蓄满就上划"的问题，缓冲要与之兼容而不是打架。

### 4.8 与既有不变量的兼容（回归清单）

`combo-move-state-machine.md` §12.5「最容易丢的七条」全部仍然适用，其中三条与本提案直接相关：

- **② 空挥不消耗冷却、不给能量、不触发被动** —— 缓冲**不改变**这一点（缓冲只改"什么时候出招"，不改"打没打到"）。
- **④ 攻速缩放的是整条序列** —— 取消窗口锚在判定结束 → 攻速变化时自动跟随，无需重配。
- **⑦ QTE 与路线系统的输入门优先级高于状态机；QTE 期间状态机必须停手并清空缓冲** —— 缓冲必须挂在 `GameplayInputGate` 之下。

## 5. 把"手感"变成可测的数

`combo-move-state-machine.md` §10.2 说"手感无法自动化"——**对"哪个更好"成立，对"有没有丢输入"不成立**。后者可以量化。

### 5.1 指标定义

| 指标 | 定义 | 采集点 | 目标 |
|---|---|---|---|
| **承诺延迟** | 手指按下 → 招式起手 | `InputManager` 记录 pointer down 时刻；`PlayerMoveStateMachine.BeginMove` 记录起手时刻 | ≤ 1 帧（16.7ms） |
| **兑现延迟** | 输入时刻 → 该输入实际出招时刻 | 缓冲写入/消费 | ≤ 0.25s |
| **丢弃率** | 合法输入中"从未兑现"的比例 | 缓冲过期计数 / 合法输入总数 | **0** |
| **提前量** | 兑现时刻 − 最早可执行时刻 | 缓冲消费时 | 越小越好（理想 = 同帧） |
| **空挥占比** | 空挥 / 总出招 | 已有 `hitAny` | 观测用，不设目标 |
| **连段密度** | 每分钟接续次数 | 埋点 | 观测用（对比改前改后） |

### 5.2 埋点方案（复用现成设施）

`Assets/Scripts/Utils/LevelTelemetry.cs` 已有 `Log(type, dict)` 的 JSONL 管线，产物在 `Library/Locus/telemetry/run-*.jsonl`，分析脚本 `Tools/analyze_level_telemetry.py`。

新增事件类型（都是轻量追加，不影响现有分析）：

| 事件 | 字段 |
|---|---|
| `input` | `gesture`、`chargeLevel`、`t`（按下/抬起时刻）、`frame` |
| `input_committed` | `gesture`、`t`、`latencyMs`（按下→承诺） |
| `input_buffered` | `gesture`、`t`、`windowStart` |
| `input_executed` | `gesture`、`t`、`delayMs`（输入→兑现）、`path`（窗口内/中立/取消窗口） |
| `input_expired` | `gesture`、`t`、`ageMs` |
| `attack_start` | `moveName`、`t`、`fromGesture` |

分析脚本加一个 `feel` 子命令：输出承诺延迟分布、丢弃计数、兑现延迟分布、连段密度。

> 机器人（`BattleAutoPlayer`）走的是 `SubmitGestureForDebug` → 同一套路径 → **机器人实测也会被这些改动影响**（节奏变快 → 难度表要重标）。

## 6. 三档方案与取舍

| | **A 保守** | **B 推荐** | **C 激进** |
|---|---|---|---|
| 内容 | 只做缓冲升级（§4.3）+ 缓冲反馈 | A + 按下即出（§4.2）+ 取消窗口与命中取消（§4.4）+ 卡肉对齐（§4.5） | B + 土狼时间 + 攻速无关的固定帧窗口 + 手势识别的重做（阈值/延迟自适应） |
| 改动面 | 状态机 + 埋点 | 状态机 + 输入层 + AttackSystem + 特效起始帧 | 全部 + 手势识别（风险最大） |

| 风险 | 低 | 中（节奏变化 → 难度表重标；教学拍要回归） | 高（手势识别改动会波及全部输入） |
| 工期 | 小 | 中 | 大 |
| 建议 | 可作为第一个可交付切片 | **主推** | 暂不做 |

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 节奏变快 → 难度表失真 | 关卡数值全盘要重标 | 每次改动后重跑 `Tools/analyze_level_telemetry.py` + 难度表；**改动与重标绑定成一次交付** |
| 缓冲跨过教学拍边界 | 打出没教过的招 / 教学卡死 | §4.7 三条硬规则；教学拍切换必清缓冲 |
| 缓冲跨过三选一面板 | 关面板那一点击变成攻击 | `GameplayInputGate` 之下；`BlockInputForFrames` 保留并加长到覆盖"按下即出"的承诺帧 |
| 改写窗口太短 → 误伤轻攻击 | 玩家觉得"莫名其妙多打一下" | 轻攻击判定帧后移到 ~20%；给改写加一个"改写中"的视觉提示 |
| 命中取消让空挥变得没有重量 | 站桩乱按 | 命中才可取消（§4.4） |
| 手势识别在连打中混淆（§16 已知风险） | Sweep/Slash/Parry 互判 | 沿用"实机调参"；`swipeChargeMode` 那类分档开关保留（当前已改为中立态禁蓄力） |
| 机器人被手感改动带偏 | 难度标定失真 | 机器人与真人两条基线分开记录 |

## 9. 需要拍板的事

1. **取消窗口是否"命中才开放"**（命中取消）？空挥是否走完收尾？
   - 开放 → 奖励打中、空挥有重量；关闭 → 节奏更自由但容易无脑乱按。
2. **轻攻击判定帧是否后移**（12% → ~20% 给改写留窗口）？代价是命中晚 0.036s。
3. **缓冲有效期 0.25s** 是否合适？（手游长动作可放宽到 0.3s）
4. **缓冲反馈**做不做？要的话是否复用现有指示器（不新增美术）？
5. **空挥是否给动作锁**？（现在空挥完全无锁 → 节奏忽快忽慢）
6. **先做哪一档**：A（只补缓冲）还是 B（推荐全案）？
