# 补齐规则（权威版）

## 术语

- **普通补齐 / 波次行军**：由战斗产生的整排清空触发的跨列移动。
- **新波次入场**：敌人先生成在逻辑目标排后方固定两排，再由独立 `SpawnEntry` owner 连续移动到各自逻辑排目标。入场不是普通补齐，不修改逻辑排队列，也不删除普通空排或开启999门。
- **普通配置空排 / 空排占位符**：波次配置中的 `(0,0,0,0,0)`。它在逻辑排队列中等同于没有活人的“死人排”，会随前方活人排死亡一起向前推进；只有当其前方已无任何活人排时才自动移除。
- **节奏门**：某排任意槽位配置专用标记 `999`；整排不生成敌人。它用于分隔同一波次内敌群，前方配置敌群清空前禁止后方跨越。
- **击退**：被命中敌人沿 row 增大的方向后移。
- **击退回位**：被击退者在停顿后返回自己因击退留下的原槽位。它不是普通补齐，也不是列内紧凑。
- **横向位移**：敌人只改变 column；除非另有明确设计，不附带 row 方向的回位或补齐。

## 规则0：普通配置空排保留开场阵型，999控制节奏门

普通配置空排与节奏门必须保留不同来源语义，不能仅凭运行时 `IsRowFullyVacated()` 与战斗产生的空排混为一谈。

- `(0,0,0,0,0)` 是普通空排占位符：开场按配置位置保留，后方敌人按配置排位直接生成；不得在生成完成后自动补齐或延迟激活后方敌人。
- 活人逻辑排整排死亡时，从逻辑队列删除该排；同一开放区段内其后所有逻辑排（包括普通空排）整体前移一格。
- 普通空排前方仍有活人逻辑排时必须保留；当前方已无任何活人逻辑排时，连续前导空排自动移除，后方活人排可在同一合法事务中继续前进。
- 示例：`A0 B1 空2 空3 C4`。A全灭后得到`B0 空1 空2 C3`；B全灭后先得到`空0 空1 C2`，再删除无活人保护的前导空排，最终`C0`。
- 示例：`A0 空1 B2`。A全灭后先整体前移为`空0 B1`，再删除前导空排，最终`B0`。
- 后排活人排先死亡时，只删除其自身逻辑节点；前方活人排和由其保护的普通空排不受影响。
- 某排任意槽位出现 `999` 时，整排视为节奏门且不生成任何敌人；若同排混填普通敌人ID，配置工具必须警告，运行时仍以节奏门处理。
- 若节奏门前方仍有任意存活且占位的配置敌人，门保持关闭，后方敌群不得越过。
- 当前方配置敌群全部清空后，节奏门开启，后方敌群才可由该合法死亡事务向前移动。
- 多个节奏门可形成更长的节奏间隔；门开启后，后方敌群连续跑完已开放区域，不在每个门之间停顿；移动必须使用正式补齐事务，不得闪现或重叠。
- `Launched` 敌人仍算前方占位；击退、击飞和横向位移产生的临时空位不能开启节奏门，也不能创建普通补齐事务。
- `WaveSpawner` 必须把普通配置空排、节奏门及配置排归属交给补齐调度器；仅扫描当前敌人对象无法可靠恢复来源语义。

## 规则1：普通补齐只由整排清空触发

仅当某排在全部列中都没有存活且占位的敌人时，后方排才整体向前移动一排。

- 同一源排中需要移动的敌人由 `ColumnManager` 统一调度。
- 某排仍有任意存活敌人时，该排不算清空，后方排不因局部空槽前进。
- 单列死亡、单列空槽、击退留下的槽位，都不能触发未受影响敌人补位。
- `Launched` 敌人仍占据原排，不能把该排判空。
- 攻击范围只决定敌人在当前排攻击还是等待，不会自行创建移动。

## 规则2：敌人是否执行已存在的普通补齐订单

当整排清空已经产生合法补齐需求后，对各敌人分别判断：

- 未进入攻击范围：执行该排的补齐订单。
- 已进入攻击范围且前方条件不要求移动：留在原位攻击。
- 正在攻击动画中：先等待当前攻击结束，再重新确认该补齐订单及目标槽仍然有效。
- 攻击冷却中：可结束冷却并执行合法补齐订单。
- 眩晕、击飞、QTE等不可移动状态：状态结束后只恢复仍有效的既有订单，不得自行创建订单。

这不是“整排阵型优先”和“攻击范围优先”的冲突：是否存在补齐需求由整排规则决定；敌人何时执行合法订单由其战斗状态决定。

## 规则3：击退只影响被击退者

击退不得触发列内压实，也不得让未受击敌人移动。

流程：

1. 记录每个被击退者的原始 `(column,row)` 槽位。
2. 检查目标槽、尾部阻塞和Boss墙；任一条件不合法则对应击退失败。
3. 命中结算：若敌人正在可打断攻击阶段且无霸体/CFrame，则先打断攻击；已经生成的飞射物继续独立飞行。
4. 被击退者移动到目标排并短暂停留。
5. 停顿结束后，只由该被击退者尝试返回自己记录的原槽位。
6. 原槽位仍合法且未被占用时回位；若暂不可回位，则保留等待或重新评估，不得把空位传递给其他敌人。
7. 未受击敌人保持原位。击退事务本身不得无条件启动全局普通补齐。

示例：`A(row0,col0)` 被推到 `row1,col0`，`E(row2,col0)` 未受击。正确结果是A回到原来的 `row0,col0`，E始终不动。

## 规则4：横向位移与击退分离

`ApplyDirectionalPush`、聚拢等改变 column 的效果不是向后击退：

- 只移动实际命中的敌人。
- 不触发其他敌人的 row 补齐。
- 不应共用“向前一排 rejoin”逻辑。
- 目标槽必须防重叠；冲突按该位移效果自己的裁决规则处理。

## Boss

Boss使用独立推进规则，不参与普通敌人的击退回位和补齐订单。

## 调度约束

- `ColumnManager` 是普通补齐和击退回位订单的唯一创建者。
- 订单必须带 owner、generation 和精确目标槽；旧回调不能推进新订单。
- 禁止把 `pendingRushMove` / `targetRow` 当作跨系统共享消息总线。
- 禁止敌人根据攻击范围、计时器、眩晕恢复或落地自行创建移动。
- 普通补齐、击退回位、横向位移、Boss推进必须使用不同调度语义。

## 已废弃的错误描述

以下旧规则全部作废：

- “仅击退触发列内紧凑”。
- “击退后按列把所有存活敌人压到 row 0,1,2…”。
- “被击退者回位后，空位继续传递给后��未受击敌人”。
- “击退结束后无条件调用 `StartWaveMarch()`”。
- “攻击中的敌人一律不能被伤害打断”。
- “横向位移与向后击退共用 rejoin”。

### 已实现：配置空排节奏门与连续 WaveMarch

- `RowConfig.IsRhythmGate` 识别任意槽位中的专用标记 `999`；`(0,0,0,0,0)` 仅表示普通空排占位符。
- `WaveSpawner` 在 PerRow 波次生成前注册本波逻辑排布局和敌人原始配置排；普通敌人先在逻辑目标后方两排生成，再通过独立 `SpawnEntry` 入场。
- `ColumnManager` 保存稳定逻辑排队列：活人排、普通空排、999节奏门；运行时位移不改变逻辑排身份。
- 普通 WaveMarch 只由“某个活人逻辑排全部成员死亡”修改逻辑队列；开场空排、状态恢复和通用拓扑通知不能创建事务。
- 活人排删除后，同一开放区段中的后方逻辑节点整体前移一格；前方无活人排时自动移除连续前导普通空排。
- 关闭的999门冻结后方逻辑区段；门前活人排全部删除后门开启并移除，后方区段由同一合法事务重新计算目标。
- 规划器以逻辑排目标与敌人物理row的差值生成精确目标槽，不从当前物理空槽推导普通补齐。
- 连续计划使用独立 `RushMoveMode.ContinuousEmptyRun`，不改变 PushReturn、Boss 和旧 PerColumn 调度语义。
- WaveMarch 活动阶段保留 owner/generation 与目标槽集合；击退暂停时保存每个成员的精确目标排。
- 已执行 Unity 完整重编译与逻辑案例矩阵验证；用户已在 `Stage_Trial` 验收普通空排推进、999节奏门和转波次远处入场。

### 已知环境差异：测试关卡阵型配置为空

- `Stage_Trial` 使用 `DefaultFormation`，因此第一排两侧不会因默认回退宽度跑出屏幕。
- `Stage_WaveMarchBugTest` 的 `formationConfig` 为空，会回退为 `(columnIndex - 2) * 2`；透视相机下 row=0 的两侧可能超出画幅。这是测试关卡阵型配置差异，不是聚拢波逻辑失效。

### 已修复：同波次大量连续敌人补齐速度过慢

- 原现象：前5排站稳后快速清空，远处敌人按一次一排、一次一人般慢慢进入；在 `Stage_Trial` 长纵队中尤为明显。
- 根因：旧 `StartWaveMarch()` 每次只创建相邻一排的 `WaveMarch` 订单，完成后才重新扫描；单列纵队被放大为长串串行移动。
- 当前实现：配置布局模式只响应活人逻辑排全部成员死亡，更新稳定逻辑队列后按目标差分创建订单；普通空排随队列前移，只有成为无活人保护的前导空排时才移除。
- 约束：仍只在原本占位排因死亡形成合法全局空排后推进；不退化为按列紧凑，不移动未受影响敌人。

### 已实现：普通空排与999节奏门分离

- `RowConfig.IsRhythmGate` 识别任意槽位中的 `999`；`(0,0,0,0,0)` 是普通空排占位符。
- `WaveSpawner` 保留逻辑配置排位；普通敌人从目标后方两排入场，普通空排与后方敌人的相对布局不被入场过程压缩。
- `ColumnManager` 依据前方配置排存活状态控制999门；门开启后由同一合法补齐计划连续跑完。

### 已验收：新波次远处入场与战斗补齐隔离

- PerRow 敌人先生成在配置逻辑排后方固定两排，随后使用 `RushMoveOrderOwner.SpawnEntry` 入场到各自逻辑目标排。
- `SpawnEntry` 不修改稳定逻辑排队列，不删除普通空排，不开启999门，也不调用普通 `StartWaveMarch()`。
- 普通敌人完成入场后才按当前逻辑排进入战斗；之后只有合法整排死亡能够创建 `WaveMarch`。
- Boss继续使用独立 `Boss` owner和既有分阶段推进，不参加普通敌人的 `SpawnEntry`。
- 用户已完成实际流程验收：转波次敌人恢复从远处入场，且未破坏普通空排、999门及后续死亡补齐。

## 当前实现校验

- PerRow 的 `ColumnManager.StartWaveMarch()` 只消费合法死亡导致的逻辑布局变更；开场生成、状态恢复和普通拓扑通知不能自行修改逻辑队列。旧 PerColumn 兼容模式仍保留历史扫描入口。
- `BeginWaveStep()` 不得按 `attackRange` 过滤源排成员；合法整排补齐需求一旦成立，源排所有合格普通敌人都应获得同 owner/generation/目标排的订单。
- 攻击动画中的敌人保留订单并等待收招；攻击结束回调只恢复已有订单，不负责创建订单。
- 攻击冷却、眩晕恢复、击飞落地和QTE结束只能执行已有订单，不能自行推导补齐需求。
- 击退回位使用精确原槽事务；旧列压实兼容入口保持 inert，不能作为普通补齐入口。

## 历史缺陷与修复

### 缺陷1：105 远程敌人攻击范围过滤导致永远不补齐 (已修复)

- 症状：105远程敌人在row2已处于 `attackRange=3` 内，前方整排清空后仍持续远程攻击，攻击结束也不补齐。
- 根因：旧实现于 `BeginWaveStep()` 使用 `rowIndex < attackRange` 跳过订单创建，导致105从未获得 WaveMarch 订单；`Enemy` 的攻击完成回调遵守所有权规则，只会恢复已有订单。
- 修复：移除订单创建阶段的攻击范围过滤。现在攻击范围不再否决整排补齐需求，攻击中的敌人会完成当前攻击后执行已持有订单。
- 验证：Unity完整重编译成功；用户回归测试暂未发现问题。

### 缺陷2：行军中被击退导致单兵永久卡死 (已修复)

- 症状：一排105敌人行军过程中，某列敌人被击退→同行军批次的其他列到达目标排后，该列敌人停在原排进入 Idle，既不补齐也不攻击，造成永久堵塞。击杀该敌人后后排恢复补齐。101（射程1）无此问题。
- 根因：行军阶段（marching）被 `AbortWaveMarch` 中断，已到达目标排的友军占据 targetRow，导致 `TryResumePausedWaveAfterPushReturns` 中 `IsRowFullyVacated(targetRow)` 为 false，暂存波次被直接丢弃，未到达的敌人永远丢失 WaveMarch 订单。同时该敌人经 `ResetRushMovementToCurrentRow` 进入 Idle 状态，在攻击范围内却无任何触发器恢复攻击或补齐。
- 伤害类型（主动/被动技能均可触发）：只要伤害路径触发击退位移（`ExecutePush` → `RegisterPushReturn`），就会触发此路径。
- 101 不受影响的原因：101 `attackRange=1`，在 row≥1 时不在攻击范围内，不会进入「攻击→OnComplete→开始行军」路径，因此不存在行军中途被击退打断的场景。
- 修复：移除 `TryResumePausedWaveAfterPushReturns` 中 `if (IsRowFullyVacated(targetRow))` 前置条件，让 `BeginWaveStep` 无条件执行恢复。`BeginWaveStep` 内部已有每敌人校验（`rowIndex != sourceRow` 过滤已到达者、`_pushReturnTransactions` 过滤 push return 中者、`AssignRushMoveOrder` 拒绝不合法者），不会对已到达敌人重复发放订单。
- 验证：Unity 完整重编译成功；待用户黑盒回归测试。
