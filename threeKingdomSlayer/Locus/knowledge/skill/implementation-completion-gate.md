# 实施任务完成门禁

## 目的

用于所有多步骤实施、调试、场景搭建、资源制作和配置修改任务。核心规则：**工具调用成功不等于任务完成；局部改动不等于可交付结果；未完成时不得用最终口吻结束。**

## 0. 开始前必须建立完成定义

在第一次修改前，写出本任务的可验证完成条件，至少包括：

1. 目标文件、对象或场景范围；
2. 需要实际观察的行为或画面；
3. 需要保存和重载验证的内容；
4. 不得修改的保护边界；
5. 失败时的停止条件。

如果完成条件不清楚，先做最小调查；只有会实质改变目标、范围或结果的问题才询问用户。普通实现选择依据项目证据决定，不因犹豫而停工。

## 1. 使用结构化任务清单

复杂任务必须使用 todo，清单至少分为：

- 现场核对；
- 实施改动；
- 最小相关验证；
- 保存/重载/回读；
- 最终保护检查与交付。

规则：

- 同时只能有一个 `in_progress`；
- 工具调用后必须更新真实状态；
- 不能因为发送了进度消息或更新了 todo 就结束任务；
- 只要还有关键项未完成，就不能进入最终回复；
- 失败后先把当前项标为阻塞或拆分修复项，不得静默结束。

## 2. 每个阶段都要形成闭环

每组改动必须遵循：

```text
读取现状
→ 记录保护边界
→ 做一个最小改动
→ 立即观察实际结果
→ 检查错误/警告
→ 回读持久数据
→ 决定继续、修复或回退
```

“编译通过”“ImportAsset 成功”“方法返回成功”“Inspector 数值正确”都不能替代最终行为、Game 画面、运行时状态或重载后的回读。

## 3. Unity 修改的强制门禁

涉及 Unity 场景、Prefab、材质、Shader、Sprite、运行时对象时：

### 修改前

- 读取当前 Editor 状态、Active Scene、所有 Loaded Scenes、dirty 状态和 Console；
- 检查 Git 状态和目标文件差异；
- 明确要保护的 Scene、脚本、移动核心、战斗坐标和用户未提交改动；
- 记录必要的对象数量、引用数量、关键哈希或快照；
- 不打开用户禁止的场景，不用整文件回退覆盖现场。

### 修改中

- 结构化 Unity 资产优先使用 Unity API / 专用资产工具；
- 场景对象修改要保留 GUID、层级、材质、引用和对象身份；
- 临时修改相机、Progress、根节点位置、显隐、材质测试参数时明确标记为临时；
- 不把 Play Mode 临时状态误当持久化结果；
- 不在一个大脚本中同时叠加多个未验证改动；
- 如果脚本中途异常，先检查是否部分写入，再决定恢复或继续，禁止直接重跑造成重复对象或重复引用。

### 修改后

至少完成：

1. 实际行为或 Game/Scene 观察；
2. Console error/warning 检查；
3. 目标层级、组件、材质和引用数量回读；
4. 保存明确授权的目标；
5. 重载目标资产或场景；
6. 重载后再次回读关键状态；
7. 确认保护对象和非目标文件没有变化。

## 4. 试验状态与交付状态必须分离

所有临时测试必须记录并在结束前恢复：

- `viewCamera`；
- `right`、`progress` 或路线预览值；
- 根节点位置和旋转；
- 材质测试参数、固定时间、调试开关；
- 临时对象显隐；
- Play/Pause 状态；
- 临时 RenderTexture、Bounds、全局 Shader 参数。

恢复顺序：

```text
停止运行测试
→ 恢复临时对象/参数
→ 恢复相机和路线预览
→ 退出 Play
→ 只保存授权目标
→ 重载并回读
```

如果临时状态无法恢复，任务状态必须标记为“未完成/需处理”，不能报告成功。

## 5. “实际可见”任务的验证标准

对于视觉、手感、动画、Shader、UI 和场景布置：

- 至少拍一组同机位 before/after；
- 动画或风动必须比较不同时间帧，静态截图不能证明持续动画；
- 画面变化必须定位在目标区域，排除相机、UI、攻击特效或其他变化造成的假证据；
- 需要验证的对象必须在真实 Game/Play 相机中可见；
- 只在 Scene 窗口看到物体不算 Game 验收；
- 只看 Transform、Bounds 或材质参数不算视觉验收；
- 视觉不明显时先确认接线、材质、相机和引用，再调整幅度或数量。

## 6. 失败恢复协议

任何工具报错、编译错误、NullReference、状态不一致或结果不符合预期时：

1. 停止后续写操作；
2. 读取当前内存和磁盘状态；
3. 判断是否发生部分写入；
4. 记录受影响对象和文件；
5. 采取最小修复或明确回退；
6. 重新执行最便宜的相关验证；
7. 只有恢复到一致状态后才继续。

禁止：

- 未检查部分写入就重复执行；
- 用“工具没有报错”推断目标行为正常；
- 把旧错误日志当成当前错误，或忽略新错误；
- 为了完成对话而跳过保存/重载验证。

## 7. 交付前硬性检查清单

最终回复前逐项确认：

- [ ] 所有 todo 关键项已完成或明确标记未完成；
- [ ] 目标行为已实际验证；
- [ ] 重要修改已保存到正确文件；
- [ ] 保存后已回读或重载验证；
- [ ] Editor 状态、Active Scene、Loaded Scenes 正确；
- [ ] 临时相机、Progress、根节点、材质测试值和显隐已恢复；
- [ ] Console 没有本轮新增错误/警告；
- [ ] Git/保护文件没有非预期变化；
- [ ] 没有把隔离测试扩大成自然流程验收；
- [ ] 仍有未完成项时，最终回复明确写出限制，不使用“完成”“已修复”“已验收”等过度表述。

## 8. 防止提前中断的沟通规则

每次长工具操作前发送一条简短进度说明，包含：

- 已确认的事实；
- 本次要做的唯一阶段；
- 完成后下一步。

工具返回后不要自动结束。先判断：

```text
是否达到完成定义？
是否完成验证？
是否完成保存和回读？
是否还有未恢复的临时状态？
```

若答案任一为“否”，继续执行或明确报告阻塞；不能发送空最终回复。

## 9. 最终报告格式

最终报告只写观察到的事实，建议分为：

1. **已完成改动**：文件、对象、参数；
2. **验证证据**：截图、回读、Console、重载结果；
3. **保护边界**：哪些没有改；
4. **未完成/限制**：自然流程、主观体验或未覆盖场景；
5. **后续建议**：只有必要时提出，不把建议写成已完成。

任务没有完成时，正常结束但明确写“未完成”，不要用沉默、空回复或模糊措辞掩盖中断。
