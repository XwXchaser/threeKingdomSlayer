# ReachAPI Seedance 2 视频生成（安全与可恢复版）

## 目的

使用 ReachAPI 官方 Seedance 2 API 生成视频。默认模型为 `seedance-2-fast`，支持纯文本、参考图片、参考视频和参考音频。Key 只能从环境变量 `REACH_API_KEY` 读取，禁止写入脚本、项目、知识库、Git、命令参数或回复。

## 官方接口

- 创建任务：`POST https://direct.reachapi.ai/v1/vids/create`
- 查询任务：`GET https://direct.reachapi.ai/v1/tasks/{task_id}`
- 文件上传：`POST https://file.reachapi.ai/file/uploads`
- 认证：`Authorization: Bearer $REACH_API_KEY`

## 默认参数

```json
{
  "model": "seedance-2-fast",
  "duration_seconds": 6,
  "resolution": "720p",
  "aspect_ratio": "16:9",
  "generate_audio": false,
  "seed": -1,
  "watermark": false
}
```

`seedance-2-fast` 不支持 `1080p`；时长必须是 `4-15` 或 `-1`。比例支持 `21:9`、`16:9`、`4:3`、`1:1`、`3:4`、`9:16`、`adaptive`。

## 参考图上传

每张本地图必须单独上传，字段名必须是 `file`，请求必须使用 `multipart/form-data`：

```bash
curl --fail --silent --show-error \
  -X POST 'https://file.reachapi.ai/file/uploads' \
  -H "Authorization: Bearer $REACH_API_KEY" \
  -F 'file=@C:/absolute/path/reference.png;type=image/png'
```

从响应的 `data.url` 读取临时 HTTPS URL。上传成功后尽快创建视频任务；临时 URL 不是永久存储。

支持 PNG、JPEG/JPG、WebP、GIF，以及音频和视频文件；单文件最大约 50 MiB。

## 创建请求

必须使用新版 `input.content`，不能使用已废弃的 `input.prompt`、`input.image_url`、`input.image_urls`、`negative_prompt` 等字段。

普通参考图示例：

```json
{
  "model": "seedance-2-fast",
  "input": {
    "content": [
      {"type":"text","text":"<可执行的镜头描述>"},
      {"type":"image_url","role":"reference_image","image_url":{"url":"<上传返回的 data.url>"}}
    ],
    "duration_seconds": 6,
    "resolution": "720p",
    "aspect_ratio": "16:9",
    "generate_audio": false,
    "seed": -1,
    "watermark": false
  }
}
```

首尾帧工作流：使用 `first_frame` 和 `last_frame`，不要同时混入 `reference_image`、`reference_video` 或 `reference_audio`。

## 参考素材规则

- `input.content` 必须是非空数组；文字用 `{ "type": "text", "text": "..." }`。
- 参考素材按角色区分：`image_url` + `reference_image` / `first_frame` / `last_frame`；`video_url` + `reference_video`；`audio_url` + `reference_audio`。
- 数量上限：最多 9 张图、3 个视频、3 段音频。
- 音频不能单独使用；“文字 + 音频”还必须至少再含一个参考图片或参考视频。
- `first_frame` / `last_frame` 不能与 `reference_image`、`reference_video`、`reference_audio` 混用。
- 单文件最大约 50 MiB；图片 PNG/JPEG/WebP/GIF，音频 MP3/WAV/M4A/AAC/OGG/WebM，视频 MP4/WebM/MOV/MKV。

## 费用与确认

创建任务会产生费用。实际发起创建前，必须向用户复述：模型、时长、分辨率、比例、音频开关、参考素材及输出路径，并取得本次生成确认。只查询已有 task 不需要重新确认。

## 防止无限轮询

创建成功后保存 `task_id`。轮询规则：

- 首次立即查询；
- 间隔 5-10 秒；
- 默认最多 12 次、总等待不超过 120 秒；
- 每次 HTTP 请求超时 20 秒；
- `success`、`failed`、`error`、`cancelled`、`canceled` 立即停止；
- 超过次数或总时限必须停止并报告当前状态；禁止后台无限轮询；
- `success` 时只读取 `data[].url`，不根据 HTTP 200 推断视频已下载。

## 稳健下载

`success` 响应中的 `data[0].url` 是对象存储/CDN 临时签名直链，视频由对象存储直接返回，并非 ReachAPI 中转。实际 host、区域、吞吐和有效时长随任务变化；签名 URL 可能约 24 小时过期，但以 URL 参数/HTTP 响应为准。完整 URL 当作凭据：只在当前进程内使用，不打印或写入日志、manifest、脚本、聊天。只持久化 task_id、对象长度、ETag、脱敏 host 和分段元数据。URL 过期时查询同一 task 获取新 URL，并重新核对对象身份；不得重新创建收费任务。

所有下载先写 `.part`，完成容器与解码校验后才原子改名为正式 `.mp4`。下载慢时先检查代理配置，并对默认线路与经确认可用的直连/代理路线做小范围短测；比较 HTTP 状态、字节数、耗时和错误，不预设浏览器、curl、代理或直连必然更快。换网络/区域节点仅是诊断候选，不保证改善。`aria2` 是可选客户端，只有确认已安装、对象支持 Range 且并发实测有收益才使用；`-x/-s` 不是默认值或加速保证。

### Range 并发下载（必须逐任务探测）

1. 查询已有 task 取得临时 URL，不创建新任务。先请求 `Range: bytes=0-0`，要求 HTTP 206、合法 `Content-Range: bytes 0-0/<total>` 且恰好返回1 byte；读取真实 total、ETag（若有）、Last-Modified 和脱敏 host。禁止使用历史大小或硬编码长度。
2. 在当前对象短测线路与 Range 吞吐。Range 不支持或并发无实测收益时退回单连接续传。
3. 并发有收益时最多从4路开始；慢对象优先约128–256 KiB小块。按实测 total 划分无重叠、连续、完整覆盖 `[0,total-1]` 的范围。
4. 每段独立文件、独立超时和有限重试；核对 HTTP 206、精确 Content-Range、total、实际字节数、ETag/对象身份。成功段立即落盘；失败只补缺失范围，不能重下全部。
5. 持久化不含 URL/密钥的 manifest：task_id、total、ETag、Last-Modified/对象标识、每段偏移、字节数、状态、尝试次数、耗时和错误。设统一单轮预算，预算耗尽就报告已有段、缺失范围和 partial 大小。状态查询、下载、拼接、解码分阶段执行，不能塞进一个长阻塞工作流。
6. URL 刷新后重新 Range 0-0，比较 task、对象标识、total、ETag/Last-Modified；身份变化就停止，不混接旧段。ETag不能泛化当作 MD5。
7. 所有段通过校验并完整覆盖范围后才按偏移拼接。验证总长度、SHA256、MP4 ftyp、顶层 box 边界及 moov/mdat，再单独完整解码；全部通过才原子改名。
8. 工具超时后先检查磁盘实际分段和 manifest，再局部恢复；不因本地超时推断服务端失败，不清除已验证进度，也不重新收费创建。

一次4路Range成功不代表新 host、任务或网络仍支持或更快；每个对象都重新探测。下载、拼接/容器检查、完整解码与视觉验收分开报告。

### 计时与解码验证

- 保存UTC阶段时间及本地monotonic耗时：上传、创建请求、任务accepted、每次状态观察、下载开始/结束、解码校验。
- `accepted → success观察` 包含排队、服务端计算、查询间隔及本地等待，必须叫观察到完成的等待时间，不能冒称纯推理耗时。若有最后一次generating时间，可提供完成时间区间。
- 总耗时应明确起止；“上传开始→下载完成”不包含之后解码检查，也不包含之前提示词准备。提升传输不代表模型生成变快。
- 可用 PyAV 完整解码，Pillow 保存原尺寸尾帧/接触表；记录实际宽高、fps、帧数、容器时长、末帧PTS。请求4秒可能包含t=0和t=4的97帧（24fps），容器时长约4.042秒，两者不冲突。
- 技术成功、抽帧观察、无缝循环验收、用户美术验收分开报告；首尾同图、低整幅差值或容器通过都不能证明无缝循环。

下载完成后必须验证：

1. 文件存在且大于 1 KB；
2. 前 8 字节符合 MP4 `ftyp`；
3. MP4 顶层 box 长度不超过实际文件长度；
4. 如可用，使用 `ffprobe` 或播放器验证可解码；
5. 全部通过后原子改名为正式 `.mp4`；失败则保留或清理 `.part`，不得声称完成。

默认输出目录：`C:/Users/steam/Videos/doubaoVideo/`。若用户指定路径，使用用户路径。

## 报告要求

成功时报告：task ID、最终状态、真实本地文件完整路径、文件大小，以及 API 返回的 usage/cost（若有）。

失败或超时时报告：task ID、最后状态、错误 code/msg、失败阶段（上传/创建/轮询/下载/校验），绝不报告 Key，也不把服务端 `success` 当成本地视频完成。

## 安全禁令

- 仅为认证从环境变量读取 `REACH_API_KEY`；禁止打印其值或持久化；
- 不把 Key 写入 JSON、脚本、shell 历史、Unity 资产或 Git；
- 不未经确认创建收费任务；
- 不把未完整验证的 MP4 导入 Unity；
- 不对卡住的任务无限轮询；
- 不自动重新生成收费视频以替代下载失败。

## 本次实测与防错经验（N3→E3、E3→EW）

## 防错经验（来自实测，任务数据见 `memory/video-generation-case-log.md`）

- 不要把请求档位等同于实际像素尺寸（实测请求 480p，Unity 读到约 560×752）。
- 最终文件 `C:/Users/steam/Videos/doubaoVideo/N3toE3_village_supply_yard_480p_4s.mp4`，3,145,128 bytes。服务端 completion_tokens=39891，cost.spend=0.22339（按响应原值记录，不擅自推断币种）。用户已验收视频。
- 时长与分辨率同时改变时不能推导单一压缩比；新生成不是原视频转码，画面也不保证完全相同。
- 首轮12次查询仍为 generating，停止的是本地等待，不是服务端生成。后续单次查询返回success。不得将本地退出码判成服务端任务失败，也不得自动再次付费生成。
- 线路择优只能在当次测速后判断：不保证直连永远更快；curl 默认线路也不等于一定走 Windows 系统代理，需核对实际代理配置。
- 下载超时的成功关键是断点续传（保留 `.part` 并用 `--continue-at -`），而不是无限延长等待或反复重头下载。
- N2→E2 v2曾将对象总长硬编码为4,920,652 bytes，实际Range探测为5,102,329 bytes，导致范围覆盖和拼接错误。必须每个task从 `Content-Range` 获取真实total，禁止复用历史大小。
- N2→E2 v3任务总长5,394,126 bytes；大分段并发工作流超时后segment0/1/3已成功，仅segment2缺失。依据已验证段补齐缺失小范围后，最终完整解码成功。状态查询、逐段下载、拼接和解码应分阶段执行；每段完成立即持久化manifest。
- 对象存储Range `0-0` 实测可返回206、真实total和ETag；不能只看 `Accept-Ranges`。不同task对象的长度与ETag不同，不得跨对象拼接。
- `data[0].url` 指向火山对象存储临时签名直链；技术说明称常见有效期约24小时，但以实际URL过期参数为准。签名URL是凭据，不存入任务manifest/日志；过期时查询同一task取新URL并重新核验对象身份，不要重新收费生成。
- 4路Range在其它任务曾完整成功，但N2→E2下载经历错误硬编码长度和长段工作流超时。并发只在逐任务测速有收益时启用；慢对象先小范围测速，约128–256 KiB分块、最多4路、逐段有限重试并立即落盘。此配置是保守起点，不保证线路带宽变快。
- 浏览器、curl、aria2、代理或直连都不是天然最快路线；aria2仅在确认安装、Range有效且当次并发实测有收益时使用。根据HTTP状态、Range/Content-Range、ETag、字节数、耗时和错误诊断，不臆测CDN或代理限速。
- Range早期尝试只得到部分数据；后续4路完整文件测试已通过且SHA256一致，生产循环视频也成功一次性分段下载。按上方探测/校验流程条件性优先4路，具体实测数字见台账；仍不可保证所有任务或网络下更快。
- 续传必须确认task、对象路径、总长度等身份一致；若URL刷新，不代表内容必然相同。保留分段manifest，不能把新生成文件接到旧分段后面。
- 每轮有总截止时间（包含请求耗时及sleep），例如轮询最多120秒、单次HTTP最多20秒，下载单轮180秒；仅循环12次加每次20秒超时并不保证总等待120秒。耗尽预算就报告并停止，不自动开下一轮。
- 下载超时优先保留可续传数据；不要像第一次重试那样直接删掉全部进度。只有完整检查ftyp、顶层box边界、moov/mdat后才改名；容器检查不等于解码或美术验收。
- 官方文档提供callback_url以替代主动轮询，但需要已授权的公网HTTPS回调服务，不接受localhost/私网地址；当前无此部署，不擅自创建外部服务。官方两份文档未提供专用下载加速或刷新结果URL接口。
- 未保存完整 prompt 时不能声称逐字复用；完整 prompt、seed、规格、首尾帧路径与 task id 必须留档（不保存 Key 与临时签名 URL）。
- 上传/创建后台命令刚排队不等于服务端已接受；只有返回task_id才报告“生成任务已创建”。只上传成功也不算视频完成。
- 子进程认证推荐通过stdin配置传入curl，避免把展开后的Key放进进程命令参数；绝不输出授权头。
- 先收到服务端 `success` 再下载；下载中断后用相同 task 与 URL 续传完成，顶层 box 校验通过后才部署 Unity。
- 本次提示词视觉验收通过的核心是“短距离、单目标、首尾帧均为真实空间锚点”。不要把首尾帧写成需要crossfade或精确贴图的两张图片；要求模型重建连接两者的连续3D环境。
- 明确物体连续性比堆叠负面词更关键：写出村内现有的车、粮袋、围栏、墙体、碎石从两侧以视差掠过并退后；树林是远处原本存在、随接近而放大的环境。并明确禁止物体无中生有、消失、背景替换、瞬移、闪烁、硬切。
- “前两秒完全保持不动”会和真实前进冲突，容易原地踏步或后段跳跃。应改为开头短暂保持起始构图，然后全程稳定向前移动。镜头限制为forward dolly only，禁止转向、横移、roll、jump。
- 对跨度较大的路线，先插入中间节点/尾帧并拆段，例如村内`E3→EW`、树林`EW→J3`；单段优先4秒480p验证。首尾帧图的实际比例应一致，本项目竖屏背景用2:3，不能在请求中混入3:4。

## EW→J3 补充经验（案例见 `memory/video-generation-case-log.md`）

- 严格首尾帧适合短距离、空间差异小的路线；当尾帧要求新增道路或分岔时，模型可能强行重排景物以贴合尾帧。
- `first_frame` 与普通 `reference_image`/`reference_video`不能混用；请求前必须按接口规则选择工作流，不能向用户承诺不可执行的组合。
- 只使用首帧时，应把目标描述为“既有道路通过镜头前进和遮挡变化逐步显露”，并明确固定相机高度、近水平视线、禁止上飘；但仍需逐帧视觉验收。
- 当模型难以稳定遵守道路拓扑时，用户后期裁剪/拼接是可接受的最终制作路径（本案例成片见 `memory/video-generation-case-log.md`）。
- 任务成功和MP4容器校验只证明生成/下载完整，不证明道路运动正确；必须实际观看或逐帧抽查后才能部署。


- 任何涉及多条道路汇入/分叉的路线视频，先用Blender建立真实道路几何并固定多个2:3摄像机，再制作像素风关键帧。
- 不再把“尾帧包含道路”当作视频会自动理解道路来源的充分条件；必须提供连续中间关键帧和可见遮挡关系。
- 以上为降低风险的制作策略，不是成功保证。实际采用首尾帧和4秒480p的EW→J3仍出现侧路瞬移，用户已否决。不能把E3→EW的一次成功归因为单个关键词，也不能把所有失败归因为单一原因。
- 缓弯路段允许相机沿道路平缓实际转向；不要照搬直路的“禁止一切转向”。统一像素风关键帧后再提交，不混用灰模与像素图作为成片首尾帧。

## J3→E4 复盘后的强制执行检查

- 道路移动视频短段默认 **6秒**；需要完成明显地形转换时先按分镜评估，N4→E11与E11→E12使用用户确认的10秒。时长不是越长越好，收费提交前逐次确认。
- 创作目标必须同时满足“开头承接上一视频实际尾帧”和“明显离开原节点并抵达新地点”。保持起点对齐不等于全程锁死构图；不得写成只走两步、始终保持原布局、禁止接近目标图。
- 使用两张 `reference_image` 时，第一张仅由提示词指定起始构图，**不是API级first_frame锁定**。不得承诺严格对齐；验收实际首帧。`first_frame` 与普通参考不可混用，若用户要求硬锁首帧，先说明接口限制再选择方案。
- 提示词按“离开原岔路→沿实际道路推进/缓弯爬升→抵达山道新环境”组织。允许真实视差和沿地形转向，不以硬切、淡化或变形替代行程。成功案例不保证其他地形组合也成功。
- 参考图必须来自已验收视频的实际解码尾帧；临时battleBackground引用不能证明当前画面。保留原始宽高，480×644或560×752都不是精确2:3；不得静默拉伸或声称同比例。
- 上传在本项目优先使用已验证curl multipart；认证通过stdin配置传入。禁止创建key.txt，即使计划随后删除也不允许。
- 创建/查询响应的 `task_id`、`status` 位于**顶层**；`data`是结果列表，成功后读取`data[0].url`。禁止递归unwrap丢弃顶层状态，禁止对列表调用get。
- 创建响应先保存去敏副本与task_id，再执行后续解析。解析失败不等于任务未创建；缺少本地记录不证明服务端未受理。状态未知不得自动重新收费创建，应恢复响应/查平台记录或明确费用未知后取得确认。
- 分开执行上传、创建、单次查询/有限轮询、下载、解码。查询得到success就明确告知用户，不把解析错误说成生成失败。
- urllib读取超时不是整个下载时限。下载使用总预算、续传及对象身份校验；保留.part，超时报告已下载字节，禁止下次以wb清零已有进度。
- 一次工具失败后先看错误和已落盘产物，再局部恢复，不反复重跑整段创建脚本。生成/下载均完成后仍须用户视觉验收才可部署。
- 每轮必须有非空交付：完成项、task_id、服务端状态、本地路径/字节及下一步。达到等待上限必须汇报，不能以空回复结束。空回复的底层原因未经诊断不能归咎于工具或服务；已知解析和超时问题与空回复分开复盘。

## E4→N4：目标参考与可控重抽

- 用户要求尾图是目标环境参考，不强制对齐尾帧时，采用两张普通 `reference_image`。起点使用上一段真实尾帧；目标图只约束夜色、地貌和战斗空地用途。此模式也不硬锁首帧，需检查接缝。
- 先明确运动方向、路径与抵达位置，再写物体的连续轨迹：沿既有道路向前、上坡、随道路左转；近景物件接近后从侧边掠过，中景逐渐展开，远山位移较小。禁止以平移图片、纯缩放、原地抖动或末秒背景替换冒充行程。
- 目标区域必须随实际移动和局部遮挡变化逐步显露，不强迫模型贴合目标图而产生硬切、闪现、变形或瞬移。
- 若总体运动已正确，仅出现局部落点问题，可在用户批准新的费用后保留Prompt、参考图与规格，只换seed做一次受控重抽。不能断言问题必然来自随机性；再次复现则检查“爬坡/平台”等词及目标图的地形暗示，而非无限抽卡。
- 本次v1末段出现高处台阶，v2保持Prompt/参考图不变后获用户验收；这是一次成功案例，不保证换seed能修复所有落差。新版本独立保存，记录实际请求、seed、task与验收结论，不覆盖旧请求记录。

## 场景路线生成：先定空间目标，再制作视频

1. **真实起点**：从上一段已验收正式视频完整解码提取末帧。战后还有夜转晨等演出时，使用最后那段视频的尾帧，不能回用入场夜景。保留原始宽高；记录来源/PTS/哈希。
2. **先画目标参考并验收**：不能只有运动关键词而没有明确的落点概念图。必要时另画中途参考。概念图仍在高处俯瞰只能作为中途，不能称为已到山脚；桥在前方与已经站在桥上是不同位置。
3. **先核对机位和朝向**：写清脚下材质、所在岸、道路方向、桥相对镜头的位置和后续动作。若任务是在桥前原地回头，反向视图应由当前空间推导，不沿用旧桥上战斗图。若旧Design与用户最新要求冲突，交接记录注明，不擅自修改Design。
4. **画风与构图分工**：已验收原始像素背景仅作独立风格参考；最新概念图作空间参考；上一段实际尾帧提供衔接。不能让风格参考中的山谷、军阵、桥面等污染目标。仅写pixel-art不够：要求可读像素簇、阶梯轮廓、归纳色块、有限色阶、硬边阴影，拒绝写实草丝/碎石/体积光。不是给写实图加像素滤镜。生成后同时检查画风和光照，风格纠正造成的晴天/时间漂移也须报告。
5. **接口契约先于承诺**：first_frame不能与普通reference_image混用。用户要求锁首帧并参考其他图时，明确选择：①仅上传first_frame，其余图转化为文字分镜；②普通多图参考，不硬锁首帧。得到确认后提交；不得把未上传的中途/尾图说成模型实际收到了，也不得为满足参数静默改模式。
6. **运动任务分类**：赶路要求真实位移/视差；夜→晨是固定机位光照变化；原地回头是固定位置旋转。不要跨类型照搬禁止词。下坡相机世界高度随路面下降，但距当地路面高度、焦距与近水平视线保持稳定；禁止航拍抬升和俯仰扫视。
7. **明确分段进度**：离开起点→经过中途→抵达终点；10秒应把后半段留给继续下降与实际抵达，不能停在中途构图。写出近物接近并掠过、中景自然显露、远景缓慢变化。禁止硬切、尾图闪现、背景替换、地形变形、纯缩放/平移。增加时长并非成功保证。
8. **去掉诱发人物的剧情词**：仅景色任务不要让模型演绎撤军、挥旗、军队/角色行动；用空路、地形、环境烟雾等描述，明确无近远景人影。对话与剧情信息留在节点系统。
9. **分开记录技术与验收**：MP4与完整解码通过不等于移动/空间/画风通过；图片输出尺寸与像素文件有效不等于美术合格。局部落点问题可经费用批准换seed重试，概念错误则先修目标图，禁止无限抽卡。
10. **交付与下载**：先报告任务ID/状态；支持Range时使用有总预算的分段下载并核对范围/总长/ETag，失败保留分段。读取PyAV duration/fps等元数据须在容器关闭前完成；关闭后报错不代表下载损坏，应只重做本地校验，不能重新收费生成。
