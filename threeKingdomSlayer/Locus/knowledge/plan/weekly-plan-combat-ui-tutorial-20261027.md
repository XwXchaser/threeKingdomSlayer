## 1. 对五项任务的理解与判断

### 任务 1 — 战斗 UI 改造

**我的理解**：现在的局内 HUD 是「**信息齐全但没有指挥感**」——血条、经验、连击、击杀、货币、技能冷却、buff、进度条
全都有，但**没有一个地方告诉玩家"我现在该做什么、按什么打"**。参考《上古卷轴：刀锋》的意义不在于抄它的美术，
而在于抄它的一条原则：**战斗屏上的一切信息都服务于"下一步做什么"，而不是服务于"把状态列全"**。

改造的核心产出应当是三件：
1. **看得懂的状态**（我有多少血、还能出什么招、敌人还剩什么）；
2. **看得见的动作**（当前这一步该按什么）；
3. **看得见的威胁**（敌人要干什么、为什么）。

### 任务 2 — 教学关优化 + 提示 UI 改造

**我的理解**：教学关现在的机制其实已经不弱（手势闸门、时停拍、防御拍、招式白名单都在），
**真正的断点是「场景里没有把新拍型配上」以及「提示的表达方式太弱」**。
本次任务 1 提供的「手势带 / 状态条」正好是任务 2 的载体 —— 两件事应该**一起设计、一起落地**，
而不是先改 HUD 再回头改教学。

玩家侧的验收口径很明确：**一个没看过说明的人，打开游戏在 3 分钟内能自己打出一场完整战斗**。

### 任务 3 — 新敌人

**我的理解**：问题不是"敌人太弱"，而是"敌人**没有立场**"。现在 1011 是靶子、1021 是盾牌、109 是冲锋，
它们各自有一个动作，但**没有一个动作能逼玩家做选择**。玩家侧技能组（戳/斩/穿刺/横扫/挑飞/招架 + 三选一 + 大招）
已经足够花哨，敌人侧必须反过来提供"读招 → 对策 → 反馈"的三段式压力。

### 任务 4 — 正式关卡配置

**我的理解**：这是本周**唯一一件"不加新内容也能提升体验"**的事，且它是任务 1/2 的验收场。
但**前置问题**：上周的难度表（xlsx v2）与两份 handoff 文档写的是 22 波，
实际资产是 6 波 —— **先对表，再配置**，否则会在错误基线上继续调。

### 任务 5 — 敌人形象重塑

**我的理解**："画风对但过于正派"是个**剪影与配色问题**，不是画技问题。
正派感通常来自：明亮饱和的配色、对称干净的轮廓、正面站姿、无攻击性。
敌化 = 破坏这四项里至少三项。1012 的接入实测数据（画布/PPU/pivot/脚底/命中帧）已经有表
（`plan/enemy1012-asset-pull-20261026.md` §8），可直接作为改造的量尺。

> - ⚠️ **未能核实**（环境限制：Fandom 有 JS 挑战、各家评测站 403/404、Steam/Nintendo 页面无内容）：
>   具体 HUD 布局、控件图标形态、"Joy / Fury" 等机制的准确叫法与数值。
>   这部分标注为「**我的既有理解**」，需要你用实机截图/录屏校准。
> - ❗ **重要纠正**：本文早期版本按"2017 / Arrowhead / 第三人称"记述 —— **均错**。
>   实际是 **Bethesda Game Studios 自研、2018 E3 公布、2019 上线、2020 出 Switch 版**；
>   **第三人称是错的 —— 它是第一人称。**
>
> **为什么这个纠正是决定性的**：第一人称意味着它的 HUD **必须全部贴在屏幕边缘**（中央是视野），
> 所以它的信息架构是"**边缘一条状态带 + 世界里的其它一切**"。
> 本作虽是 2.5D 侧视，但结论一样成立 —— **HUD 不该往中央堆**。
> 注意：我们的 `ChargeIndicator`（蓄力环）**是跟随手指的**（`ChargeIndicatorController.UpdatePosition`），
> 不是固定在中央 —— 这一条我早期写错过，已修正。**但结论不变**：屏幕中央应当留给战斗与引导光圈。

### 2.1 它到底是什么（✅ 已核实）

- **Bethesda Game Studios 开发、Bethesda Softworks 发行**的免费 ARPG，2018 E3 公布，
  2019-03-28 iOS 抢先体验、04-05 开放注册、05-02 免账号、2020-05-12 正式版、2020-05-14 Switch 版；
  **2026-06-30 服务器关停**（即：现在已无法实机对照，只能靠资料）。
- **第一人称**，非第三人称。
- **线性**结构（刻意放弃开放世界，因为移动端限制），三种模式：
  - **Town** = 主城/枢纽（接任务、见 NPC、重建城镇）；
  - **Abyss** = 无尽地牢 roguelike（刷等级与强度，与剧情无关）；
  - **Arena** = PvP 1v1。
- 地牢**手工关卡 + 程序生成**混合。
- 战斗输入：**点按 / 滑动 / 虚拟双摇杆**（触屏），官方描述为"几乎无法回避的一对一战斗"。
- 战斗手段三类：**近战武器 / 法术 / 远程**；**最多同时装备 3 个法术**。
- 横屏竖屏都可玩。
- 明确**移除了**潜行、搬尸、偷窃与隐藏物品等行为。

### 2.2 实机截图读解（✅ 2026-10-27 用户提供实机图，竖屏 412×810）

**这张图是本次最重要的参考资料** —— 它把 §2.2 从"我的既有理解"变成了可核对的硬事实。

参考的局内 HUD 一共**只有 5 个元素**：

| 位置 | 元素 | 实测细节 |
|---|---|---|
| **左上** | **罗盘** | 菱形外框 + 内部横线（Elder Scrolls 经典指北 / 等级指示） |
| **顶部居中** | **命名精英敌人的血条** | 上方是敌人名 `SPRIGGAN`，下方一条长条：**左侧灰白段（已损血量的残影）+ 中段红（当前血量）+ 右侧黑（已损失）**，白色描边 |
| **左下** | **一个"大招就绪"指示** | 蓝色菱形 + 白色刃状符号。**只有一个**，不是招式列表 |
| **底部** | **三条状态条** | 魔法（蓝，左半宽）+ 耐力（绿，右半宽）并排一行；**生命（红，整条通栏）**在最下面一行 |
| **屏幕中央** | **格挡盾牌图标** | 米白色盾形（圆顶尖底），临时出现 |

**从截图读出的三条结构性事实：**

1. **参考的 HUD 只有 5 个元素，本作局内目前有 15+ 个。**
   差距不在"功能缺失"，在"**数量**"。我们的信息是**全量摊开**，它的是**极简切片**。

2. **"招式"在参考里不是一排图标，是"一个就绪的大招指示"。**
   它的法术通过**轮盘呼出**，HUD 上只常驻"那一个最重要的"。
   → 这解释了它为什么能这么空，也提示我们：**不必把 6 个招式全摆出来**。

3. **中央的盾牌是「状态显示」，不是「输入按钮」。**
   它不写"按这里"，它写"**你正在格挡**"（居中、临时出现、无按钮底）。
   → 与用户"格挡是固定按钮"的理解略有出入，但**对本项目的结论完全一致**：
   **不设固定格挡按钮**。理由不是"参考没有"，而是本作的格挡/防御本就是**手势触发 + 长按姿态**，
   根本不需要输入按钮；参考的中央位置用来告诉我们"**你现在的状态**"。

**与用户本周规划的对齐度**：用户提出的四条（招式在左 / 血量在下 / 不设格挡按钮 / 只有 BOSS 显示血量）
**与截图几乎逐条吻合** —— 说明方向是对的。差别只在"我们比参考多一层"：
参考的左下是**一个**就绪指示，我们要放**一排 6 个招式**（因为本作的手势词表比它宽得多）。

### 2.3 它的战斗是被骂的，这决定了我们能学到什么（✅ 已核实）

媒体评价是分裂的，这一点非常关键：

- IGN（Jagneaux）：骂**加载慢、刷取 grind、缺乏创新、微交易**；但**明确表扬了画面、角色、剧情和战斗**。
- Nintendo World Report（Rairdin）：**重批战斗与玩法**，称其"a downright joke"。
- Nintendo Life（O'Reilly）："a bland and repetitive grind"。
- Digitally Downloaded：措辞极重。
- Switch 版 Metacritic 为"普遍差评"，OpenCritic 仅 8% 好评。

**读出来的结论**：这个参考**不是一个战斗手感标杆**。它的战斗被大量批评为
"僵、重复、触屏不精确、一对一消耗战"。**所以不能把它当成"我们的战斗该长什么样"的模板。**

它真正值得学的是三样**信息架构**的东西：

| # | 它的做法 | 为什么成立 | 本项目怎么用 |
|---|---|---|---|
| **A** | **HUD 只保留"视线可回收"的一小块**（左上一条三色带），中央永远留给战斗 | 玩家的视线中心就是战斗区；信息放在中心 = 挡战斗 | 玩家状态收成**一条**；中央留给战斗与引导光圈（`ChargeIndicator` 跟随手指，不冲突） |
| **B** | **不按"招式"组织 HUD，按"此刻相关的动作"组织**（最多 3 个法术槽） | 3 是**信息预算**，不是平衡设计：逼玩家做取舍得舍，屏幕也才装得下 | 本作有 6 招式 + 三选一 + 大招，**更需要**"此刻相关"这一层，而不是把 6 个图标全摆出来 |
| **C** | **反馈尽量放进世界**（敌人头顶血条、命中点伤害数字、地上可点的回状态图标） | 因果同框 → 不需要 HUD 变胖 | 敌人血条已有；连击里程碑 / 气力回收可做世界漂浮物，替代常驻计数 |
| **D** | **多选项用轮盘，不用按钮排** | N 个选项不占 N 个按钮位 | 本项目的三选一、道具、主动技能组都可用"轮盘/卡片"思路，而不是加常驻图标 |
| **E** | **没有教程关，靠"即时提示"（动作第一次重要时才出现）** | 教的是**当下要用的那一个动作**，不教抽象规则 | 本作已有脚本教学关；再补一层**正式关的即时提示**（项目已把它列为"另立项"：`plan/tutorial-gesture-ui-implementation-20261026.md`） |

### 2.4 不可照搬的部分

| 参考项目 | 本项目 | 结论 |
|---|---|---|
| 羊皮纸 / 金属 / 西幻符文 UI | 三国水墨 / 毛笔 / 木板 / 竹简 | **只借信息结构，不借皮肤** |
| 第一人称 + 双摇杆 + 3D 场景 | 2.5D 侧视 + **纯手势**（无摇杆） | 不要引入虚拟摇杆；本作的手势词表比它丰富得多 |
| tap=攻击 / swipe=格挡 / hold=蓄力 | 手势 → **招式表**（`MoveTableConfig`）→ 6 个不同招式 + 连招状态机 | 本作的核心是**手势 → 招式**的映射，UI 必须能表达"哪个手势对应哪一招"，这是它没有的维度 |
| 战斗深度来自装备/附魔/吼叫 | 战斗深度应来自**招式组合 + 敌人机制** | 别学它的养成 |
| 敌人多样 = 敌人数量 | 敌人多样 = **行为多样** | 直接对应任务 3 的判断（见 §7） |
| 刷取 grind 养装备 | 三选一 + 天赋 | 不要学 |

### 2.5 对参考项目的三条总结（→ 本周方案的总纲）

> **结论一句话**：《上古卷轴：刀锋》值得借的是**信息架构与教学时机**，
> **不**是它的战斗手感、美术皮肤、养成结构。
> 它的战斗是被骂的 —— 我们不能拿它当战斗标杆；但它的"HUD 极简 + 反馈在世界 + 即时提示"三件事，
> 恰好是我们现在最缺的。

1. **屏上只保留一条"一眼看完"的状态带，其余信息移到世界或移到动作发生时。**
   （对应现状问题：底部木板占屏 23%、10 个 buff 位挤在右下、招式图标全关导致"我能不能出招"不可见。）
2. **不按"招式"组织 HUD，按"此刻相关的动作"组织。**
   （对应现状问题：6 个技能图标在 prefab 里全关、玩家不知道自己现在能出什么。）
3. **教学分两层**：脚本教学关（保证动词学会）+ 正式关的即时提示（保证动词在真实压力下也想得起来）。
   Blades 只做了第二层；**我们两层都做**，这是本作相对参考的真实优势。

### 6.2 引导光圈：把教学提示升级成「局内即时提示」

**参考的做法（已核实）**：**没有教程关**。敌人一出现，在合适时机弹出光圈/提示，教当前这一个动作。

**我们要做的两件事：**

1. **教学关**：把现有提示的表达方式改掉 —— 从"一只大白手指着敌人"改成
   **在屏幕下方（招式区）对应格子上原地循环演示**，并配文字。
   `TutorialGestureHint` 已有 `PlayTap/PlaySwipe/PlayHold/PlayChargedSwipe/PlayParry/PlayParryHold`
   六个方法 —— **能力够，摆放位置要改**。
2. **正式关**：新增**局内即时提示** —— 玩家**第一次**遇到需要某个动作的情况时，
   在**敌人身上**弹光圈提示该动作，学过一次后**永不再弹**。

> 这一项项目里**早已立项但没做**：`plan/tutorial-gesture-ui-implementation-20261026.md` 的
> 「不做（另立项）」列写着「**正式关首入拍**（C2 复合手势提示 + 破霸体教学）」。
> **用户这次的 U5 正是那一项。**

#### 6.2.1 触发规则（建议，待你拍板具体条目）

| 触发 | 提示内容 | 依据 |
|---|---|---|
| 第一次遇到 **109 骑兵冲锋** | **上划招架**（竖滑轨迹 + 光圈） | 109 是"必须用招架才能解"的敌人 |
| 第一次遇到 **1021 盾卫** | **蓄力上挑破盾**（蓄力光圈收缩 + 上挑轨迹） | 1021 的盾是硬门槛 |
| 第一次遇到**远程敌人** | 横向闪避（若任务 3 落地远程兵） | 依赖任务 3 |
| 第一次遇到**霸体敌人** | 重攻击破势 | 依赖任务 3 |

#### 6.2.2 三条硬规则（不做就会变成干扰）

1. **一次性**：学会后**永不再弹**。需要一个"已学会哪些动作"的存档位 ——
   项目已有天赋存档机制（存 nodeId，安全），可复用同一套写法。
2. **不打断**：玩家正在出招 / 正在对话 / 正在三选一 / 正在结算 → **排队**，不抢占。
3. **不遮挡**：光圈落在**敌人身上**（像参考那样），用**描边光圈**而不是全屏遮罩；
   且不能落在玩家的操作区（下方手势带区域）。

#### 6.2.3 实现要点与风险

| 项 | 说明 |
|---|---|
| **复用而非重写** | 建议把 `TutorialGestureHint` 的 ring/finger/trail 抽成一个**通用"手势提示器"**，教学关与局内提示**共用同一组件与同一套视觉**，只由"谁触发"区分（否则两套并存会重复/互斥） |
| **世界 → 屏幕的桥** | 光圈要落在敌人身上 → 需要世界坐标转屏幕坐标。项目已有现成做法：`TutorialGestureHint.Place()` 的屏幕定位、`TutorialStageDirector.PlayerScreenPoint()` |
| **触发判定放在哪** | 放**数据层 / 导演层**，不放 UI 层 —— 遵守 `memory/unity-project-understanding/ui.md` 的「不在 UI 里写业务规则」 |
| **存档时机** | "学会"的判定点 = **玩家成功做出该动作一次**（不是提示播完）→ 避免"看了没做，下次还弹" |
| **与 U5 的验收关系** | U5 的验收口径：**玩家在正式关第一次遇到新敌人时，不需要外部说明就知道该做什么** |

### 6.3 教学关 + 局内提示的统一视觉

既然两者共用组件，视觉语言也要统一 —— 参考只有 5 个元素的极简，
我们的提示也应该是"**一个光圈 + 一条轨迹 + 可选一行短字**"，而不是层层叠叠的蒙版 + 压暗 + 多层 UI。

## 7. 任务 3：新敌人开发（本周只出方案）

### 7.1 问题定位

玩家侧已经花哨，敌人侧必须补**"互动"**。判定标准（三条同时满足才算一个合格新敌人）：
1. **可读**：玩家在 0.5 秒内能看出"它要干什么"（有预警、方向明确）；
2. **可解**：存在至少两种对策（不是只能靠数值硬吃）；
3. **有反馈**：对策奏效时必须有区别于普通命中的表现（音色/顿帧/破防条/击退）。

### 7.2 建议的新敌人清单（每个都写清三段式）

### 13.5 过程中的坑（值得记）

1. **场景里的 HUD 是 prefab 实例且有 157 处手改 override** —— 改 prefab **不会**同步到场景。
   → 做法：把改造写成**可重跑工具**，场景实例与 prefab 模板用同一套函数各跑一次。
2. **在 prefab 实例里"删了重建"会产生 added override 并逐次叠加** —— 我一度堆出 3 个 `LevelOrb`、3 对 `HealthFillLeft/Right`。
   → 做法：工具改成**「有就复用、只改属性；没有才新建」**（幂等）。
3. **`anchoredPosition` 相对的是「锚点参考点」不是「枢轴」** —— 我按"卡片中心"算坐标，结果元素全跑到屏幕外。
   → 锚点 (0,0) 的元素，`anchoredPosition.y` 是**离父级下边缘多高**。
4. **子节点的 `sizeDelta` 传错导致尺寸翻倍** —— 拉伸锚点下 `sizeDelta` 应为 0；固定尺寸要用锚点 (0.5,0.5)。
5. **槽位锚点要用 (0,0.5) 而非 (0.5,0.5)** —— 否则 `anchoredPosition.x` 相对的是父级中心，左对齐失效。
6. **层级路径在不同 prefab 版本间会变** —— `ButtonFace/Icon/CooldownDim` 的实际父子关系与预期不同，改用**按名深度查找**。
