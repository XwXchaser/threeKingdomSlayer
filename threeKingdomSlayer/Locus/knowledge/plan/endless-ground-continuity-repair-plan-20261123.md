## 0. 一页接手摘要

### 0.1 用户要的结果

无尽关沿路线持续向前行进，左右分支均可玩；不论当前位置、走到哪一圈，玩家脚下和前方都能看到**连续、正常、与沿途环境相符的路面**。圈尾内容向下一圈内容过渡时，不能出现石板/土路交错、道路缺口、整屏突变、纹理突然旋转或明显重洗。**剧情关保持原样。**

- 圈是**节点与素材复用**，不是让道路几何闭合或玩家回头。
- J1 左路是 EV → N3 村庄石路，右路是 N2 官道；保留玩家选择、节点出口确认与旅行流程。
- 地面是画面的一部分，前方道路与两侧景物必须在空间和时序上协调；不能只修脚下、忽略远处。
- 验收以真实 Game 画面与连续旅行表现为准；内部几份 mesh、采什么坐标是实现选择，不是用户目标。

### 0.2 已确认三个独立故障

1. **村庄土路/石板交错：**运行中同位置把地面复制半径从 1 临时改为 0，交错消失。已证实问题与相邻圈地面同时覆盖相关；不要仅凭“朝向不同”断言具体深度机制。
2. **圈尾材质整屏变化：**当前材质为 `350 / 26`，以 flat z 判断；沿路 380 m 圈边界对应 flat z 约 `328.623 m`，中心线到换圈时淡出尚未开始。单地面对照出现整片石路 → 整片土路。
3. **圈尾贴图跳变：**临时将淡出试为 `300 / 28` 后两侧均是土路，仍能看到纹理方向和图案切换；后续圈和右支也有同类现象。

这三个问题应拆开诊断，但修复必须作为**一个完整的空间连续结果**验收；只改 `copyLapRadius` 或只调石板参数都不算完成。

### 0.3 严禁把实验假设升级成设计

- **不能直接规定“地面全局必须只有 1 份”**。半径 0 只是有效的故障隔离对照；单份整地面按圈切换可能把下一圈路面等到圈点才显示。需求是“各空间区域被正确、唯一地绘制且前方连续”，实现上允许合理的单份、多份或切片，必须证明无重叠、无空洞、无整屏跳变。
- **不能对所有 `YLapFollower` 强制半径 0。** `N1 Far Landmarks` 当前为 1，服务于远景预显示，不能随地面一起改。
- `300 / 28` 是已经试过、值得继续验证的**实验值**，不是用户已确认的最终参数。
- “接缝区双坐标采样/纹理混合”只是**备选研究方向**，并非已选方案；若出现透明双重纹理、游动、全屏渐变或材质不对应，必须否决。
- **不能恢复旧的环路图、合流点、黑幕或玩家回头；不能新增额外 UI、过场或自动跳过。**

## 1. 设计准则与任务边界

### 1.1 必须保持

1. **无限向前、节点/素材复用。** 一圈终点前后空间与朝向连续，不走回头路；“回 N1”是下一次素材出现，不是闭合几何。权威口径见 `design/endless-mode-design.md` §1、§2.1–2.2，以及 `design/route-extent-and-content-source.md` §3。
2. **分支选择与节点流程不变。** 保留 J1 左 EV/N3、右 N2，以及战斗结束后的出口确认 → 旅行 → 抵达；纯情景节点的现有处理也不改。代码中圈分数记账后进入下一圈，不恢复旧的圈结算 UI。
3. **剧情关不变。** `Finite + 手工` 是受保护的现有路径，变化前后相同进度、同一路线与同一拍摄条件下目标为逐像素相同。无尽特有逻辑不得写穿共享材质、场景或有限模式的视觉。
4. **保留地图空间纹理基线与路面风格。** 石板路、黄土路及路肩各自可辨识；不要把整条路换成另一种外观来遮问题。
5. **预显示而不是全屏换景。** 前方该出现的道路与景物必须在玩家到达之前出现在正确的位置；不要在圈号跳变的一帧把整个可见范围都替换为另一帧。
6. **相机与战斗坐标不改。** 维持视点固定、世界迎面而来的既有投影模型，不通过移动 Battle Camera、Player 或 Enemy 遮接缝。
7. **有限/无限 × 手工/随机的长期扩展空间保留。** 此任务不要求实现四格架构或地面切片生产管线，也不允许把新实现做成未来只能适配某个固定圈数、固定左路或某个 hard-code 关卡。
8. **不加新玩法。** 不动波次、难度、三选一、掉落、存档、输入、UI 或圈结算规则；不能添加黑幕、镜头遮挡等未授权演出。

- `design/endless-mode-design.md` 的“每圈面板”“几何闭环”等有旧段落；§2.2 明确废弃几何闭环，`EndlessRunController` 较新注释与实际实现显示已取消每圈结算面板。不要依过时部分回改玩法。

- 本交接仅记录和规划；如要更新 Design 文档，需取得用户对设计文档修改的明确授权。实现后也不得未经授权把本执行计划的建议改写为既定设计。

## 4. 技术问题模型：先定义世界空间的归属

以下是设计思路与数学约束，不是要求照抄的实现。

### 4.1 避免重复绘制，也避免换圈才加载前方

对镜头能看到的每一个地面空间位置 `P`：

1. 先明确它属于当前内容片还是前方下一片，以及石板、土路与路肩分别应是什么。
2. 在硬切/交界处保证**没有两个不受控的地面表面争夺同一像素**，也没有无人负责的洞。
3. 若确需混合，只允许有意设计、局部且连续的**同一空间位置上的材质过渡**；不能让两个表面深度竞争或通过全屏渐变掩盖切片不对齐。
4. 当玩家距圈界还有可见距离时，前方应已经是下一片应有的道路和布景，而脚下仍属于当前片；过渡应随空间被走过，不能由 `CurrentLap` 一变化就把整个可见区域替换。

### 4.2 正确处理坐标与边界

- 令 `F_k` 为第 k 圈内容从自身路线坐标到路线根坐标的刚体帧，则同一个 `P` 对两圈有 `q_k = inverse(F_k)·P`、`q_(k+1) = inverse(F_(k+1))·P`。计算前先把世界坐标转换到**路线根空间**；不要把 world XZ、投影后相机空间和 mesh 局部坐标混成一种。
- 同一平面位置在不同圈会有不同的纹理坐标与材质判断。`i.map.y` 是局部 flat z，**不是**沿路距离；圈结束平面或路线纵向距离必须按真实路线和左右支求解，而不是直接 `localZ == 380`。
- 画面横向并非只有道路中心线。要验证路心、路肩和屏幕边缘；弯曲段、分叉区域的最近点和法线判定可能有歧义。现有 `AlongRoute()` 是针对左支的三候选实现，右支/不同圈/远离路心时不能盲目复用，必须测试。
- 第 0 圈脚下/身后必须有地面：不得无条件把 `map.y<0` 全裁掉。已有失败尝试正是在开局裁空脚下。
- **左右分支每圈可重新选择。** `route.right` 是当前分支状态，`YScrollSample.EnsureLapFrames` 会以它参与帧缓存重建；是否足以正确表述跨圈历史、下一圈未选择分支的帧，必须在真实流程及左右混合圈验证。不要预先硬编码下一圈方向或用本圈分支无条件推导将来分支；发现设计/运行时缺口需报告，不可顺手重写路线玩法。
- `flatCycleLength`、场景起点变换、转角与材质实际配置可能改变。不要把 `380`、`328.623`、`45°` 或一次实验数值散落硬编码，除非仅用于测试期的当前基线。

### 4.3 当前 `350/26` 的隔离风险

当前石板淡出直接由材质值控制，Shader 中不是完整地以无限模式开关隔离。**不要直接把共享材质永久改为 300/28 后便声称剧情关零变化**。应先记录有限模式当前真实画面，再设计无尽专用的计算/配置路径；有限路径必须沿用修改前的行为。若要新增参数，应能在 Inspector/资产引用中追溯，不引入 `Resources.Load`、静态资源缓存或字符串资产查找。

## 5. 推荐解决路径与备选方案

### 5.1 推荐先做：确定真实边界和单一归属

目标是保留现有路线、相机、纹理和布景系统，**最小化改动**地实现“同一可见地面位置有明确的责任方”。建议先按 §6 做隔离原型与完整矩阵，再选一种：

**候选 A：按真实空间边界切分相邻地面**

- 保留提前存在的当前/下一地面，但以同一条经验证的空间边界或等价规则划分它们，各自只画负责的部分；不是简单照抄 `map.y < 0`。
- 地面外观按对应片自身坐标取样；石板收尾与开头土路在边界附近的空间区间内一致。
- 重点验证：弯道、左右分支、路宽及路肩上的边界；首圈负向部分单独正确覆盖；多圈实例在前方预显示而不 z-fight。
- 风险：如果只把沿路距离最近点当作整张大平面的全局坐标，可能在分叉、远离路心和拐弯边缘产生错误归属或空洞。算法须通过明确样本，不成立就换方案。

**候选 B：单个可见地面载体里按空间采样当前/下一片**

- 保留单个绘制载体，但在可见平面上按固定空间边界分别计算当前和下一片内容；跨圈时几何载体切换不能改变可见区域原有的像素归属。
- 必须证明前方下一片道路会提前出现在正确的空间位置，而非 `CurrentLap` 变化时整幅换图；对石板、土路、路肩、外侧全部考虑。
- 若只对贴图坐标做跨圈插值，仍可能改变道路边界、混出虚影或在大平面范围错位。先证空间归属，不能把“纹理颜色更像”当作解决。

**候选 C：切片/过渡地面**

- 若 A/B 无法满足现有画面，可评估用地面切片及按距离调度实现相邻片端部匹配，或在必要处设计明确的石→土过渡段。
- 先考虑现有素材和已有管线，不为本次缺陷擅自启动全量 `YRouteSlice` 架构重构。若需要新增美术素材、改变村庄石板覆盖范围/风格，或新增用户可见的过渡表现，**先向用户说明取舍并获得批准**。

### 5.2 纹理连续性：只有在覆盖归属成立后再处理

- 地图空间 UV 为默认基线，非接缝区域保持现有外观。
- 可研究接缝前后同一位置的两套局部坐标，计算受限的空间材质过渡；但不得仅凭同一颜色就判定成功。
- **风险明确：**插值会出现两套颗粒叠影、纹理相位“游动”、边缘拉伸或大面积淡变；同时石路/土路、路肩过渡应与环境空间一致。实时行进下任一现象明显即失败。
- 备选是让相邻材质/切片在接缝空间拥有兼容的纹理端部，而不是旋转全图或以世界 XZ 覆盖全部道路。是否需要新的过渡素材属于待用户决策。

### 5.3 不要重新做已证伪尝试

除非有新证据且先隔离验证，不要：

1. 把全部地面 UV 改成 `(along, dist)`：远离路心时路肩/外侧会被拉伸、发歪。
2. 把全部地面 UV 改成世界 XZ：路线每圈旋转后纹理相对道路旋转。
3. 无条件使用“沿路裁剪 + 半径 1”：曾裁掉开局脚下负坐标。
4. 用黑幕、整屏渐隐、强行旋转相机、几何闭合或改变路线长度来盖住接缝。
5. 通过关掉村庄石板、让所有道路都用黄土来获得表面上的连续。

## 6. 分阶段执行计划

### P0：保护现场与重建基线

1. 重读本文件、设计红线和源码；`git status`，记录 HEAD、Editor 状态、已加载场景、dirty 状态。用户未保存内容不得覆盖。
2. 通过 `unity_yaml_read` / Unity API 确认目标场景、地面对象、材质的身份和引用；如果场景未加载或索引不可用，不要把零结果当真。结构化 Unity 资产用 Unity API 修改，不要通过通用文本工具改 YAML。
3. 真实入口可能改写 `PlayerPrefs`，测试前读 `SaveManager` 与可能的存档写入路径，准备可核实、可恢复的存档保护；不要调用清档或破坏现有存档。确认场景与 Prefab 的原有未保存状态。
4. 用现有 Game 视图、Battle 主相机采集有限/无限基线；记录画幅、相机、路线、进度、分支、圈号、copy 状态、场景/摄像机列表。截图先用已知不同状态证明实时。
5. 不要在正式 `YJunctionSample` 中直接开展不可控试验；优先临时 runtime 状态或隔离实验场景/开关，必须清楚哪些更改会持久化。**不新建相机/灯、不写 `RenderSettings`。**

### P1：证明空间覆盖和圈界

1. 收集左右支、多圈（至少第一、第二次跨圈，以及左右交替时）的当前圈/下一圈坐标、帧、地面 renderer、mesh 范围与片元边界。
2. 选择 `P` 样本：路心、左右路肩、视野左右边缘、脚下、前方，覆盖 J1/弧线、村庄、出村、圈界前后与下一圈开局。判断应由谁负责以及是否缺口/多重覆盖。
3. 对比候选 A/B 在首圈负坐标、左支/右支、相邻圈不同朝向、近/远范围的可行性；避免直接依据 circles 或 `Renderer.isVisible` 得出可见性。
4. 明确下一圈分支尚未选择时可用的信息，以及切换 `route.right` 后旧圈帧/地面有何变化。若影响空间一致，先报告根因与最小方案，不扩展改玩法。

**出关条件：**能解释 330 m 交错、圈界两侧材质归属、首圈脚下和左右支画面；方案不依赖同一坐标被两块无控制重叠的平面抢画。

### P2：实现最小范围修复

1. 在隔离原型中一次只改一个变量：地面区域归属 → 石板收尾 → 接缝纹理连续；先后用 §7 的证据检查。
2. 石板转土必须是**路线空间中的合理位置**，保证村庄仍有石路并与建筑匹配；`300/28` 只作起点，需在真实画面确认。
3. 不同模式分支/材质配置应保证有限模式沿用原逻辑；地面对象的参数校验应与最终方案相符，**不能在方案未定时把“半径 0”固化为架构规则**。
4. 若需新增/变更序列化字段，先查 C# 与 `unity_code_usages`（含 UnityEvent / AnimationEvent 等）并保留已有资产数据和引用。不要为诊断随意改名、删组件或重建带 GUID 的资产。
5. 正式修改前检查共享材质用途、Prefab 来源和覆写；只改授权目标，不覆盖用户现有内存改动。源码应用需按冷/热修改规则编译，Inspector/测试前完成 domain reload。

### P3：按验收矩阵回归并整理交付

1. 运行自动化数值/覆盖测试及 Game 截图对照；再沿真实无尽入口走节点确认、左右分支与正常旅行。程序快进仅作补充，并标明未覆盖。
2. 有限剧情关同进度 before/after 逐像素对照；截图时间点和采集方法必须一致、自检有效，不能复用旧误报结果。
3. 连续越界检查物件、纹理、路面，至少覆盖 0→1、1→2 两次换圈以及左/右分支跨圈组合；实际走更高圈并监视对象生命周期。
4. 查看 Console、确保地面/远景/段加载无退化；恢复测试时临时状态，退出 Play，核对相机灯光清单、场景 dirty、磁盘时间戳与 Git diff。
5. 交付说明必须区分已验证、用户需主观验收、未覆盖项和风险；不要把无尽关大系统的其他工作顺手完成或宣称通过。

## 7. 截图与测试纪律（非常重要）

### 7.1 禁止为截图造摄像机

- 复用现有 `Main Camera` + `unity_capture_viewport(target=game)`。项目明确禁止 `unity_execute` 中新建任何 GameObject、Camera、Light 进行截图，也不要修改 `RenderSettings`。
- `YScrollSample` 在 `Camera.onPreCull/onPostRender` 控制 `_YSEnabled`，新增探针相机和直接 `Camera.Render` 可能触发 `Restore()`、渲染出非实际投影分支，不能用于判定真实路线。
- 每次临时变更只作用于 Play 实例，记住原值；必须确保异常也能恢复。绝不修改共享资产后依靠退出 Play 恢复。
- 结束后回读相机、灯光与场景列表，确认只有原有对象；检查 `Assets/Scenes/*.scene` 与 Y 场景、材质的状态。

### 7.2 截图有效性自检

1. 比较开局与村庄、或同位置切换可验证的地面状态；必须确实显示出预期差异，且能回读对应运行时状态。若结果几乎一样、拿到纯色或过时画面，应判失败而不是推断结果。
2. 记录实际 Game 分辨率、场景/相机、分支、进度、圈号、地面对象和采集时间。必要时关 HUD 做**补充隔离图**，同时保留正常完整画面；不要把纯地面实验说成完整游戏体验。
3. 检查地面时可在 Play 中暂时隔离非地面 Renderer，必须逐项记录并恢复；但最终仍需正常景物和 UI 的完整 Game 图，防止只在隔离状态成立。
4. `Texture2D.GetPixels32()` 比较前按交接纪律显式深拷贝各帧，并先用两张明显不同的画面确认比较器有响应；更可靠的是分别保存、回读独立 PNG 并计算差异。不能让同一复用数组和自身比较。
5. 同一位置的有限模式 before/after 可要求 0 像素差；**跨时间行进帧本来就会变化，不能机械要求全部像素相等。**对连续运动，结合地面局部画面、采样位置、正常相邻帧差分基线和肉眼连续播放共同判断，屏蔽粒子/动画只能作为辅助而不是捏造通过。
6. `unity_capture_viewport` 的单次调用有延时，前后两次调用不是游戏相邻帧；需要真正逐帧序列时应研究现有安全采集方式并核验帧号/时间戳，不允许为了方便新建渲染相机。
7. 修改 `progress` 后段调度/窗口需多帧收敛；历史上向后跳不会卸载导致状态污染。定点实验应尽量单向前进或重开 Play，并明确它不替代自然旅行。
8. `Renderer.isVisible` 对被强行撑大的包围盒可能恒真；Renderer 开启数量也不能证明地面实际有覆盖或画在屏幕中。

### 7.3 采集和存档留存

- 过程数据放 `Library/Locus/tmp/`，文件名注明分支、圈数、距离、条件、帧号；用户需要长期留存时再明确交付位置。`Library/Locus/Screenshots/` 会淘汰，不能当永久证据。
- 真实无尽入口可能执行存档及结算代码；测试前后核对 `SaveManager` / `PlayerPrefs`，不要删档、修改用户进度或调用会产生持久奖励的路径而不保护状态。
- 不要复制硬编码用户存档内容进文档或日志；只记录必要的状态、对照 hash 或恢复状态。

## 8. 必须覆盖的验证矩阵

| 类型 | 位置/条件 | 通过要求 |
|---|---|---|
| 无尽开局 | 第 0 圈、脚下与身后负坐标 | 地面覆盖完整，N1 土路正常，无意外露底 |
| 分叉前 | N1 → E0 → J1 途中 | 原有道路和两侧景物时序正常，没有未选支路的错误提前覆盖 |
| 左支入村 | J1 左转、EV 到 N3 | 石板路与村庄连续、不与黄土随机交错；路心与路肩不拉伸 |
| 左支出村 | 从石板到土路的完整空间区间 | 淡出跟随道路位置，不能整屏交叉淡变；村庄仍有应有石板 |
| 左支跨圈 | 至少 0→1 与 1→2，圈界前、中、后 | 视野内有当前与前方合理道路，圈点无石→土整屏突变、纹理突然换相位或可见闪烁 |
| 右支跨圈 | N2 官道→下一圈，至少一次 | 土路方向/图案连续，不受左支石板判断污染 |
| 左右交替 | 不同圈选择不同 J1 支路 | 帧、道路、景物与历史分支保持一致；不假定未来分支 |
| 首尾边缘 | 开局及圈界附近的脚下/前方/左右路肩/屏幕边缘 | 画面无裂缝、无深度闪烁、无裁剪硬边、无纹理拉伸 |
| 正常流程 | 选关进入无尽，战斗或合规快进、玩家确认出口、旅行、进入下一圈 | 不跳过用户选择、不新增圈结算面板、不改变玩法或临时 Build |
| 剧情关 | 相同进度与相机，N1/J1/左右相关可达段等 | 修复前后逐像素 0 差；若无法严格相同，标注原因并回查，不可只凭“看起来差不多” |
| 运行时稳态 | 至少 10 圈的相关计数与 Console | 参考 `design/route-extent-and-content-source.md` §4；记录活跃数、实际保留实例数、窗口登记数，而不是只看 active。发现既有问题要区分本次引入与原有问题 |
| 自动检查 | 坐标转换、覆盖、branch、边界、开局负坐标、有限/无限 | 测试通过；性能关注帧循环/Shader 成本，不添加不必要分配 |

**对象生命周期注意：**当前 `YLapFollower.EnsureCopies` 会关闭超范围副本而不销毁，`_copies` 留存；不能用“活跃数稳定”证明不存在累积。若 10 圈发现既有常驻增长，先确认是否由本修复造成并报告；不擅自扩大本次范围做无关重构。

设计文档中“前方 40 m renderer 非零”和“相邻帧物件数变化 ≤5”等指标可作为回归辅助，但它们本身无法证明地面纹理连续，也可能受统计范围/刷新时序影响；最终必须结合真实空间画面与逐帧时序。

### 12.3 根因分解：三个相互独立但关联的问题

#### A. 全局 `right` 使历史圈帧被改写，副本又不重摆

- `YScrollSample.EnsureLapFrames()` 以当前 `right` 为 `frameCacheRight` 并生成唯一 `lapStep`；一旦 `right` 改变，它清空帧表，再把**所有历史圈**都按当前分支重新组合。
- `ScrollRoutePresenter.ApplyLane()` 在玩家选右路时设置 `route.right=true`。在本次从第一圈左路进入第二圈后，第二圈 J1 定点切右时，`TravelPosition` 在同一距离从约 `(-261.31,462.97)` 跳到 `(261.31,462.97)`；`GetLapFrame(1)` 从左侧 `(-126.96,328.62), -45°` 改为右侧 `(126.96,328.62), +45°`。
- `YLapFollower.CreateCopy()` 只在创建副本时套一次圈帧；`EnsureCopies()` 对既有副本只激活，不在分支改变时重摆。因此第 1 圈 c1 地面仍在 `(-126.96,-1.8,328.62), 315°`，当前帧 API 却认为它应在 `(126.96,-1.8,328.62), 45°`，位置差约 **253.9 m**。c2 差约 **898.2 m**。
- 在 N2 `646.1165 m` 的运行时采样：当前代码给 Shader 的第一圈全局曲线近似距离 `s≈628.096`，要求由 c1 负责；但 c1 在这个点的自身 mesh 局部 z≈`-37.66`（网格下界 `-25`），不覆盖该点。c0 网格覆盖，但 `k=0` 在 `s>380` 被裁除。即使 Renderer.enabled=true，Game 仍没有地面。
- 同一 `GetLapFrame` 还被 `YRouteSegments`、`ScrollRouteNodePresentation`、`YRouteStreamingWindow`、`RoutePropFollower` 消费；不能只修地面复制而让布景、锚点和相机继续使用不同的帧。

#### B. Shader 的 `AlongRoute` 仅认识第一圈路线，不能判任意圈归属

- `YGroundJ1Branches.shader` 将未投影的路线根坐标 `i.rpos` 送入 `AlongRoute(i.rpos, _YSBranchSign)`，该函数只含一条位于第 0 圈原点的直线/弧线/尾段。得到的标量即便对同一世界点在各副本中数值相同，也**不等于**真实多圈折线路线的总沿路距离。`k*L` 裁剪依赖的前提不成立。
- 持续右支的 CPU 数学对照（复刻当前 Shader 公式）：实际 `710 m` 时得到 `s≈673.3`；实际 `760 m` 时 `s≈708.6`；实际 `1520 m` 时 `s≈724.3`，误判为第 1 圈责任区，而当时活跃地面为 c3/c4/c5。Game 截图确认该高圈点无地面，即使相关 c3/c4/c5 帧/位置与当前 `GetLapFrame` 一致。
- §11.2 的“CPU 镜像 shader 全部恰好一份”不能替代真实路径与**实际 mesh 覆盖**的独立测试；该历史统计声称的覆盖与本轮实际截图相矛盾，需要重新设计判据，不要重复沿用。

#### C. 石板淡出使用了跨圈绝对量；土路纹理仍各按圈局部旋转

- `stoneExit` 在无限分支比较同一 `along` 与一次性区间 `L-(width+shoulder)-fade → L-(width+shoulder)`，没有按每圈的本圈局部进度计算。左支第 1 圈村庄实际局部 `325 m`（总 `705 m`）时 Shader `along≈669.73`，区间约 `366.05→376.05`，因而 `stoneExit=0`；实际图中石板消失。
- `_Road/_Shoulder/_Outer` 仍用每个副本自己的 `i.map/4` 取纹理。相邻**圈副本**的局部坐标基向量随圈帧旋转，因而接缝两侧即使颜色都是土路，方向/相位仍不同。§11.3 第 2 条声称“只剩沿路 UV 一条路”**不是已证实结论**；全图沿路 UV 和全图世界 XZ 已分别出现拉伸及相对路面旋转，不能当作默认方案。

### 12.4 修复目标与不可越界的设计

1. 玩家一路向前；“回 N1”只表示内容复用，不做几何闭环、回头、合流、黑幕或镜头跳转。
2. 每一圈 J1 左右由玩家重新选择：左 EV/N3 为石板村庄，右 N2 为土路官道；保留节点出口确认→旅行→抵达。圈分数记账后现行为直接下一圈，**不恢复旧圈结算面板**。
3. 修复须同时消除混支路 Game 缺地、高圈裁空、后续村庄石板丢失和接缝纹理方向错误；不得以取消石板、隐藏地面、镜头遮挡或整屏淡变回避。
4. `Finite + 手工` 剧情关现有表现逐像素不变；不动战斗、奖励、掉落、输入或存档语义，不做全量路线架构重写。
5. 保留完整前方预显示：道路与两侧布景在空间和时序上匹配；不能以“单帧有地面”或“Renderer.enabled”作为通过标准。

### 12.5 推荐技术方案：圈帧历史 + 局部归属 + 真实纹理连续

**这是待实验的工程方案，不是已实现结论。** 用最小闭合链解决根因；以下名字只是表达契约，不强制新增某个公开 API 或数据结构。

#### 阶段 A：为每圈保存稳定的路线起点与本圈分支

1. 概念模型：`F_0 = Identity`；第 k 圈保存实际确定的分支 `branch_k` 和起点帧 `F_k`；出圈步进 `S(branch_k)` 由既有 `Evaluate(L, turnAngle, branch_k)` 得到；**`F_(k+1) = F_k.Compose(S(branch_k))`**。本圈 `branch_k` 只决定这一圈从 J1 之后如何走以及未来圈入口，不得反过来改动 `F_k` 和更早的已确定帧。
2. 以 J1 的玩家选择作为**本圈分支提交时机**；先读实际入口/事件调用链，确保它只影响当前圈的未来，已走过的空间与 J1 前相机姿态不变。`route.right` 如仍保留，明确它只是当前圈选择/兼容视图，不能再用它重算历史。
3. `GetLapFrame(k)`、`EvaluateRoute(distance)`、节点锚点、地面、段调度、窗口和补给投影必须消费**同一份圈历史**。有限剧情关保持原算法/输入语义，不得因无尽历史引入画面差异。
4. 下一圈的**入口帧**只依赖本圈已定分支，在靠近上一圈终点、内容需预加载前可确定；但下一圈 J1 的左右分支**尚未选择**。预览下一圈共用主路，不得硬编码未来 J1 分支或提前提交玩家选择；依真实内容装载链决定如何保持可见区域稳定。
5. 明确生命周期：一局开始/结束清空会话历史，跨圈保留该局必要历史；退出后不额外持久化。参数重设、开关 endless、route 切换、检查点/测试直接跳距以及暂停恢复，先按实际调用者定义确定行为。**不能凭空给未经过的圈补齐玩家选择并当成真实历史**；对于诊断跳距提供明确的测试输入/构造历史，无法确定时应报告而非静默猜测。
6. 已生成且属于已确定历史的副本应继续匹配稳定的 `F_k`。分支变化只可能使**当前圈尚未确定的未来内容**需要调整：检查预生成/缓存的地面副本、段 prefab、远景、锚点和投影；通过稳定帧或有界刷新保证一致，避免把屏幕内物件批量移动。需要时先复现并确定哪些属于未来，不能以“把所有副本按当前 right 重摆”修复。
7. 当前 `RoutePropFollower` 每帧用 `CurrentLap`；窗口 `SetTrackedDistance` / `RebuildDistances` 含路线根/世界坐标假设；一并检查各消费者，但只改本任务所需的最小依赖，保证宝箱及节点不回归。

**单元/数值验收：**左右序列 LL、RR、LR、RL、LRL、RLR；在新圈 J1 切支路前后 `F_0..F_current` 的已确定起点不变（允许浮点误差），J1 处相机位置/朝向连续；下一圈起点由本圈真实选择得出；`F_k.Inverse(F_k.Apply(p))≈p`；用户选择不得改写历史，重启新局后历史不泄漏。

#### 阶段 B：地面覆盖和石板按各圈真实局部坐标判断

1. **先解决责任域，不先改 UV。** 每份地面及当前/相邻圈共享来源一致的帧 `F_k` 与该圈分支，使用投影前路线根坐标变换到对应圈局部：`q_k = inverse(F_k)·p_route`。对 q_k 用该圈分支的路线形状计算本圈局部 `s_k`；**不要**对整个路线根空间直接套第 0 圈 `AlongRoute`，也不要把 `flat z` 与沿路距离直接等同。
2. 局部距离仅能表示“相对该圈路线”的距离；**单独要求各副本判断 `0≤s_k<L` 不自动保证不重叠或无缝**，因为相邻圈是不同坐标系、平面可以大面积交叠。必须构造共享、互补且互斥的空间归属，例如使用同一个真实接缝位置和切线/半平面作为相邻圈的共同边界，再结合该圈有效内容域；也可用其他经验证的方案。跨弧、宽路肩、首圈负坐标和相邻圈多向旋转要明确边界，不得伪造“自动互斥”。
3. 由同一条实际圈帧链产生上一/当前/下一圈的边界和 per-copy 变换；使用每 Renderer 的 `MaterialPropertyBlock` 或等价可追踪方式传递必要的圈局部信息。若修改 MPB，先 `GetPropertyBlock`、只更改自己负责的属性、`SetPropertyBlock`，不要覆盖其他系统既有 per-renderer 属性；不用新全局材质复制影响剧情关。
4. 第 0 圈的脚下/身后仍有地面；后续圈前方提前出现且不同时绘制共面片元；布景和地面保持同一坐标真源。必要时明确最近路径段与真实可见走廊的适用范围；用**实际 mesh/裁剪共同验证**，不能只把 shader 公式 CPU 镜像一遍后声称通过。
5. 对石板入场/收尾，使用**负责该地面片的本圈局部坐标/进度**，只在无尽路径生效；检查每圈左支村庄仍是石板、出村区自然转土、右支永远不是误叠石板。参数 `10`、`300/28` 都不是最终视觉验收值；大幅改变石板视觉范围需先征求用户。
6. 性能：不要对所有历史圈每像素扫描；可仅对实际可见的相邻圈/接缝送入有限数据、预先计算矩阵/切面。评估移动端顶点/片元开销，记录实测而非假定。

**覆盖验收：**以独立 `EvaluateRoute` 的真实圈路径 + 相邻 Renderer 的实际变换、mesh 范围及 Shader 裁剪验证；对路心、±路肩和屏幕左右边缘、脚下与前方采样：应有恰好一个责任表面，边界容差要明确且不能依 `clip(0)` 让两面共绘或一面留缝。关注几何投影、曲面顶点密度和裁剪方向，实际 Game 截图/连续旅行必须复核。

#### 阶段 C：单独解决接缝土路的方向/相位

1. 以用户反馈的“路面应直、不能出现斜向错纹”为观察目标：对相邻圈同一条道路空间接缝前后、路心和路肩采样土纹方向及相位，而不是只看石板占比、颜色 R−B 或整帧平均差。
2. 保留非接缝区域的现有地图空间 UV；先在隔离原型比较至少一种局部做法：例如只在接缝附近为当前/下一片建立兼容的局部坐标或相位对齐，或受限的空间过渡。具体映射必须使用两圈真实帧与其相邻接缝的朝向，保证**静态世界点的纹理不会随玩家靠近而整屏游动**；不能通过简单把 UV 在两个坐标系之间直接线性插值就宣称无畸变。
3. 不恢复全路世界 XZ、全路 `(along,dist)`；过去分别造成每圈相对路面旋转和路肩拉伸。若局部方案仍有斜纹、重影、模糊、拉扯、闪烁或材质前后不符即否决。保留现有结果和失败证据，再评估切片端部纹理对齐/专门过渡素材；若需新增美术或明显改变已有道路视觉先问用户。
4. 验证以空间中经过的接缝为准：接缝应随前进自然从远至近通过画面，不是玩家进入新圈时全屏颜色/纹理变化。采集正常速度及适当慢速**连续 Game 序列**；用户最终主观验收方向和自然度。
