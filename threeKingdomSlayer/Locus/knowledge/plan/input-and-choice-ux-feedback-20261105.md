## 1. 预输入（#1）—— 现在只有"半套"

### 现状（有缓冲，但只覆盖一种情况）

`Assets/Scripts/MoveSystem/PlayerMoveStateMachine.cs`

| 位置 | 行为 |
|---|---|
| L31 `bufferEnabled = true` | 开关默认开 |
| L52-53 `_hasBuffered` / `_bufferedInput` | **只有一个槽位**（后来的一次覆盖前一次） |
| L152-159 `Update()` | 窗口打开的那一帧消费缓冲 → 执行 |
| L193-194 | 窗口已开 → 立刻执行 |
| L196-208 | `t < 窗口起点` → **缓冲**（这是唯一的缓冲入口） |
| L211 | `t > 窗口终点` → 「窗口已关闭（不响应）」→ **直接丢弃** |
| L185-189 | 手势**没有匹配的边** → 「无匹配边（不响应）」→ **直接丢弃，连缓冲都不占** |
| L287 / L426 | `BeginMove()` 与 `ExitToNeutral()` 都把 `_hasBuffered = false` → **招式一结束，缓冲就没了** |

`Assets/Scripts/Player/Combat/AttackSystem.cs` L424-427：动作锁期间的新输入
`if (!cancelCurrentMove && _actionLockTimer > 0f) return false;` → **静默丢弃，玩家完全不知道刚才那一下被吃了**。

### 所以现在的缺口是四条

1. **没有跨招式的缓冲**：招式打完（`ExitToNeutral`）后，之前存进去的输入已经被清掉 → 玩家"提前按"的那一下不会在下一招补上。
2. **只对"有匹配边的手势"缓冲**：Jab1 只有 Tap→Jab2、Hold→StabR2 两条边 → 在 Jab1 期间划一下（想接斩击）= 直接消失。
3. **窗口一关就丢**：接续窗口过后（招式后摇）输入 = 直接丢，没有"记住 0.2 秒，等能动就出"。
4. **动作锁吃输入没有反馈**：玩家按了没反应，游戏不提示"早了"。

### 标准动作游戏的预输入长什么样（对照差距）

- 任何攻击输入在"不能出招"期间都进缓冲，**存活 0.2~0.3 秒**；
- 角色一恢复可动（动作锁结束 / 取消窗口打开）的**第一帧**就打出；
- 缓冲期间给玩家**可见反馈**（招式图标高亮 / 枪口预亮），玩家知道自己"按下的那一下被记住了"；
- 缓冲是一次性的（打完就清），不会累积成"搓招队列"。

### 改法方向（供拍板，未实施）

- 在 `PlayerMoveStateMachine` 把单槽 `_hasBuffered` 升级成"**带时间戳的缓冲**"（`GestureInput.timestamp` 已有现成字段），并加一个 `bufferLifetime`（建议 0.25s）→ 过期就丢。
- 缓冲入口放宽：**不要求有匹配的边**（先记下来，等窗口/中立态再判能不能执行）。
- 缓冲消费点扩展到"**动作锁结束**"（`ExitToNeutral` 之后的第一帧）→ 这就是"预输入"。
- 加"缓冲中"的可见反馈（需要一个小 UI 元素，**依赖美术**）。
- 动作锁吃输入时给反馈，而不是静默。

**代价与风险**

- 缓冲会让"乱按"更容易打出招 → 可能让教学关的手势闸门更难控（教学里 `TutorialAttackGate` 只管招式白名单，不管手势白名单 → 需要一并确认）。
- 缓冲 + 现有"按住蓄力"语义有冲突风险：缓冲里存的是 `charged` 等级，延迟执行时蓄力语义会过期（现在的 `chargeLevel` 是随按住时长实时算的）→ **建议只缓冲"未蓄力"的普通攻击**，蓄力招式仍要求实时按住。
- 机器人（`BattleAutoPlayer`）走的是 `SubmitGestureForDebug` → 同一套缓冲逻辑 → **机器人实测的节奏会变**，之前标定的难度表可能要重跑。

## 2. 招式不跟手（#3）—— 延迟来自三处叠加

### 2.1 点按是"抬手才出招"

`Assets/Scripts/Player/InputManager.Pointer.cs` L113-120：鼠标抬起 → `ProcessGesture()` → 出招。
→ 手指按下到角色动起来，中间是**玩家自己按住的时长**（60~120ms 常见）。这是最直接的"延迟感"来源。

> **关键发现：「按下即出轻攻击」的模型当年设计过，但没接上。**
> `AttackSystem.TryCancelLightAttackStartup()`（L192-205）与 `StabSweepEffect.TryCancelBeforeHit()`（`StabSweepEffect.Hit.cs` L34）都在，
> **全工程没有任何调用点** → 这套"按下先出、滑动可改写"的机制是死代码。
> 也就是说：**按下即出**这件事不需要从零设计，脚手架已经在了。

### 2.2 连招的第二下要等窗口开

实测 `Assets/ScriptableObjects/Moves/MoveTable_Zhangfei.asset`（经 Unity 读出）：

| 节点 | 时长 | 接续窗口 | **窗口真正打开的时刻** |
|---|---|---|---|
| Zhangfei_Jab1（轻攻击戳） | 0.45s | [0.65, 1.00] | **0.2925s** |
| Zhangfei_Jab2 | 0.40s | [0.00, 1.00] | 即时 |
| Zhangfei_StabR2（指向突刺） | 0.66s | [0.55, 1.00] | 0.363s |
| Zhangfei_Slash（斩击） | 0.50s | [0.55, 1.00] | 0.275s |
| Zhangfei_SlashC2 | 0.66s | [0.55, 1.00] | 0.363s |
| Zhangfei_Sweep（横扫） | 0.55s | [0.00, 1.00] | 即时 |

→ 玩家在 Jab1 打出后**立刻**再点一下：这一下会被缓冲，但要**等到 0.29 秒后**窗口打开才真正出招。
→ 主观感受就是"我点了，它没动，过一下才打出来" = **不跟手**。

### 2.3 空挥与命中的节奏不一致

`AttackSystem.TryExecuteAttack` L470-525：**只有 `hitAny`（打中敌人）才设动作锁**；
空挥 → L522-525 直接 `return false` → 状态机 L268-272 判定"未执行（空挥）"→ **整段招式根本没开始**（无动作锁、无状态机节点）。
→ 打中 = 被锁 0.45s；打空 = 完全不锁、下一下立刻能出。
→ 节奏忽快忽慢，玩家会认为"有时候反应快、有时候慢"。

### 2.4 改法方向（供拍板，未实施）

| 子项 | 做法 | 代价 |
|---|---|---|
| A. 按下即出 | 把「按下即出轻攻击」接上：pointer down 就起手，抬手时若手势不成立再取消（`TryCancelLightAttackStartup`） | 需要重排 `ProcessGesture` 的 gate 顺序；防御键与 UI 点击要排除 |
| B. 提前开窗 | Jab1 的接续窗口起点从 0.65 调到 ~0.35~0.45（命中帧之后立刻能接） | 会改变连段手感与"空挥不推进段位"的既有约束 → 要和设计文档 `design/combo-move-state-machine.md` 对齐 |
| C. 取消窗口 | 命中后给一个 0.1~0.15s 的"可被下一招取消"窗口（动作游戏常见 cancel window） | 与动作锁、`repeatSelf` 规则耦合，改动面大 |
| D. 空挥一致性 | 空挥也给一个（更短的）动作锁，或至少让状态机节点照常推进 | 会让"打空也能连"变容易 → 影响难度表 |

**我的建议**：先做 A + B（低风险、直接对着"延迟感"），C/D 留到 A/B 验收后再看需不需要。

## 3. 教程不该"点任意处都能继续"（#2）

### 现状

`Assets/Scripts/UI/BattleDialogueView.cs`

| 位置 | 行为 | 问题 |
|---|---|---|
| L80-86 | 裸 `Input.GetMouseButtonDown/Up` → 任意位置按下再抬起就 `Advance()` | **不查 UI 命中**：点战场、点敌人、点任何按钮都会推进台词 |
| L89-92 | `OnPointerClick`（本组件）→ `Advance()` | 点气泡本体推进（这条是合理的） |
| L63-72 | 教学台词**自动推进**（`_tutorialAutoAdvanceMinSeconds = 2.2` + 每字 0.16s） | 教学台词本来就会自己走完 |
| L50 | `PointerAdvanceEnabled` | 只有"手势拍"期间会被关掉（防止做手势的那一下把台词点没了） |
| L22-23 | `_advanceButton` / `_skipButton` | **已经有明确的「继续」按钮**，但上面那条"任意处"路径把它架空了 |

### 根因

三条推进路径并存（自动推进 / 任意处点击 / 点气泡），而**最宽的那条（任意处）没有 UI 命中检查** → 玩家的战斗手势（点敌人）会被当成"跳过台词"。

### 改法方向（供拍板，未实施）

- 删掉/收窄 L80-86 的裸输入路径：推进只认 **① 点气泡本体**、**② 点「继续」按钮**、**③ 教学台词的自动推进**。
- 裸输入路径若要保留，必须先做 UI 命中检查（`EventSystem.RaycastAll`），并且**排除战斗手势区域**（项目里 `InputManager.IsPointerOverUIAt` 已有同类判定可复用）。
- 教学气泡上加一个"点击继续"的视觉提示（**依赖美术**）。

**代价与风险**：改成必须点气泡 → 新手可能不知道要点哪里 → 要有提示；教学流程里凡是依赖"随手一点推进"的拍要逐条回归。

## 4. 三选一改长按选择（#4）

### 现状：确实是"两次点击"

`Assets/Scripts/UI/UpgradeChoicePopup.cs` L68-81 `OnCardClicked`：

```
第一次点卡 → 选中（抬升 + 高亮），不生效
第二次点同一张卡 → ConfirmChoice() → 真正应用
```

`Assets/Scripts/UI/UpgradeCard.cs` 用的是 `UnityEngine.UI.Button`（L99-104 绑 `onClick`）→ **天生只有"点击"语义，没有"按住"**。

### 改法方向（供拍板，未实施）

- 卡片改成 `IPointerDownHandler` + `IPointerUpHandler`：按下开始计时（建议 0.3~0.4s），按住期间画进度（环形填充 / 卡片充能），到时**直接应用**；提前松手 = 取消（不选中）。
- 首次按下就高亮（给"正在选择"的反馈），松手未满时回弹。
- **教学要同步改**：`TutorialStageDirector.cs` L591-593 `TryGetChoiceScreenPoint` 会把手势提示落在推荐卡上 → 长按语义下，提示要表达"按住这张卡"，否则新手会点一下就松手 → 教学这一拍会卡住（教学用 `SetChoiceSelectable` 只放行推荐卡）。
- `Button` 组件可以保留但不再用它的 `onClick`，改用 `EventTrigger`/自写 handler。

**代价与风险**：每次选择多 0.3~0.4s（一关 10+ 次 → 多几秒）；长按与"拖动取消"的手感要做出来；**需要美术**（进度指示）。

## 5. 三选一改到波次结束弹出（#5）—— **好消息：架子已经在了**

### 现状：升级立刻打断

`Assets/Scripts/Core/UpgradeChoiceManager.cs`

| 位置 | 行为 |
|---|---|
| L196-197 `Start()` | 订阅 `PlayerState.OnLevelUp` |
| L202-208 `OnPlayerLevelUp` | **立刻** `_pendingLevelUps++` → `StartChoiceFlow()` |
| L231-258 `StartChoiceFlow` | `Time.timeScale = 0` + 生成弹窗 → **战斗当帧冻住** |
| L216-229 `TriggerItemChoice` | Boss 锦囊（物品三选一）→ 同样立刻弹 |

→ 玩家正在砍人，经验满了 → 画面冻结、弹窗盖上来 → **体验断档**（用户原话）。

### 已经存在的"波次结束"挂点

`Assets/Scripts/Managers/StageRunFlow.cs` L187-199 `OnWaveCleared`：

```csharp
if (ucm != null && ucm.IsChoosing)   // 有待处理选择 → 等选完再出下一波
{
    ucm.OnAllChoicesDone += OnChoicesDoneSpawnNextWave;
    return;
}
WaveSpawner.SpawnNextWave();          // 否则直接出下一波
```

→ **"波次结束 → 弹三选一 → 选完 → 再出下一波"这条链已经写好了**，只是现在很少走到（因为升级总是提前把弹窗弹了）。
→ 路线流程也走这条：`FakeRouteRuntime` 用 `StageController` 当战斗宿主（`FakeRouteRuntime.cs` L8/L101）→ 同一个 `StageRunFlow`。

### 改法方向（供拍板，未实施）

1. `OnPlayerLevelUp` 改成**只入队**（`_pendingLevelUps++`），不立刻弹、不暂停。
2. 在 `OnWaveCleared`（波次清空）时统一 flush 队列 → 弹窗（此时暂停是合理的，因为战斗本来就要停一下）。
3. 升级的**即时反馈**不能丢：HUD 等级数字本来就会更新（`BattleHUD.cs` L94 → `UpdateExpLevel`）；建议再加一个轻量"升级了"提示（不打断）。
4. 物品三选一（Boss 锦囊）跟着同一队列走（Boss 死 = 波次结束，天然对齐）。

### 代价与风险（**这一条风险最多，必须逐条验**）

| 风险 | 说明 |
|---|---|
| 最后一波 / 关卡结算 | 如果波次打完了还没 flush，升级会丢 → 结算前必须 flush 一次 |
| 教学关的三选一拍 | 教学用 `forcedChoices` + `Choice3@0` 存档标记，且教学波很短 → 波末弹出时机要和教学拍对齐（**教学拍目前可能就是靠"升级立刻弹"触发的**） |
| 路线流程 | 节点战斗结束后是否还有"波次清空"回调？需要在路线里跑一遍确认 |
| 连续升级 | 一次波里连升 3 级 → 波末要连弹 3 次（现有 `_pendingQueue` 已支持，但 UI 要能连着弹） |
| 难度标定 | 波内不再被打断 → 玩家的 DPS 曲线变了 → **难度表 / 铁律八要重测** |
| 机器人 | `BattleAutoPlayer` 等待"选择完成"才继续（`FakeRouteRuntime.Node.cs` L153 判 `IsChoosing`）→ 流程改动后机器人的波次节奏会变 |

## 6. 优先级建议

|---|---|---|---|---|
| 1 | **#5 三选一改波次结束** | 架子已经在（`OnWaveCleared` 就有等待逻辑），收益大 | 中 | 中（教学拍 / 结算 / 难度标定） |
