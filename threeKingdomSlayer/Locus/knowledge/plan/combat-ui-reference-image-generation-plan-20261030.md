## 二、美术方向基线（写进每一张提示词）

来源：`design/art-style-guide.md` §7（UI 与 HUD）+ §9（验收标准）+ §5（色彩关系）。

| 维度 | 规定 |
|---|---|
| 气质 | **近黑底衬（墨黑 #1A1A1E / 冷铁灰 #3C4450）+ 米白 #F2EDE0 细描边**承托信息；红色用于生命、危险、攻击确认；**暖金 #C8A03C 只留给本身就该是暖色的元件**（铜钱本体、黄色菱形槽内面、重要数值）；数字与文字干净、高对比、易读 |
| 描边规则 | 每个元件都是**外深内亮**：最外 1 像素近黑描边 + 内层 1~3 像素米白线；拐角是**像素阶梯**不是圆角 |
| 禁止 | 萌系、圆润玩具感、仙侠水墨、欧美奇幻、现代科幻、照片写实；UI 不得堆成厚重面板遮挡战斗 |
| 关系 | 与战场共享"厚重、战争、街机动作"气质；不与角色精灵共用像素密度（UI 可以更干净） |
| 验收 | 不看文字也能认出用途；轮廓优先；有明确视觉焦点；场景不遮挡战斗 |

> 现有可当"UI 语言参考"的已验收资产：`Assets/Sprites/UI/Hub/hub_v9_*`（落地页 V9，14 件，2026-10-25 用户签收）。

## 四、生成路线（三条，建议 A 为主、B 为辅、C 兜底）

### A. AI 生成**美术效果稿**（整屏）—— 本方案的主力产出

- **输入**：`R1_actual_1080x2160.png`（真实实机帧，几何已正确）
- **方式**：`/v1/images/edits`（multipart，字段 `image[]`）**单图编辑** —— 让模型"保留所有元素的位置与尺寸，只把 HUD 重绘成目标美术风格"
- **为什么用 edits 而不是 generations**：几何必须锁死；纯文生图必然重排
- **必须写进 prompt 的不可改变项**：左下角的等级球/头像/棱形排、通栏血条、左上暂停键、右上铜钱 —— **位置与尺寸一律不变**；只换质感与配色
- **风险**：模型会重绘局部、可能移动元素 → 生成后**必须做几何比对**（见 §六），偏移超 ±3 canvas 单位即判失败

### B. 人工/AI 辅助精修单件 —— 拆件后逐件收

- 拆件后按 §三 规格做**规整**（对齐、裁切、补边、纯色化、去光晕）
- 这一步是**像素级确定操作**，用 Pillow 脚本做更稳（可复算、可复跑）

### C. 程序化生成 —— 纯几何件

- 棱形（`hud_slot_diamond` 已有 144×278）、血条纯色（`hud_bar_fill` 16×16 已有）、球（`hud_orb_circle` 128×128 已有）
- **只需换配色与加质感层**，不必再生成 → 省成本、保证几何

> **建议比例**：C 覆盖 8/11 件（1、2、3、4、5、6、9、10），A 覆盖 2/11（7、8），B 做全部 11 件的规整与收尾。
> 也就是说：**付费生成只花 2 件的钱**，其余靠程序化 + 规整。

## 六、生图调用与验收（可直接执行的参数）

### 6.1 调用参数（项目默认，来自 `skill/gpt-image-generation.md`）

```text
model:      gpt-image-2.5-sunburst
endpoint:   POST https://api.muskapis.com/v1/images/edits   (multipart/form-data, 字段名 image[])
quality:    max                 # 项目统一档位，不降档
input_fidelity: high           # 编辑/融合用
size:       1024x1536          # 竖屏整屏稿；单件可用 1024x1024
background: transparent        # 仅当需要原生透明（单件件用）
output_format: png
n: 1
```

- 环境变量 `MUSK_API_KEY`（本机已存在，**不得写入仓库/文档/日志**）
- 输出目录：`<当前用户>/Pictures/gptGen/`（本机 = `C:/Users/steam/Pictures/gptGen/`），版本化文件名 + 同名 `.response.json`
- 本环境**没有 requests**，用标准库 `urllib` 手工拼 multipart（模板见 skill 文档）

### 6.2 透明与路由（必读，避免重复付费）

- 透明能力**取决于本次落到哪套后端**，不取决于模型名：G1/G2 返回原生 RGBA，**B 后端一定返回 RGB 且把棋盘格画进像素**
- 判据：响应回显含 `background` → 多半原生 RGBA；不含 → 多半 RGB 棋盘格。**机器读 PNG Color Type（6=RGBA，2=RGB）才算数**
- 拿到 B 后端时：**不要连发**，隔一段时间再试（同段落可能整体落在 B 上）
- 追加"禁止画棋盘格"prompt 条款**无效**（实测），别靠堆 prompt

### 6.3 两级验收（引用 skill 原文，不重复造轮子）

- **一级（机器）**：PNG 可读；Color Type = 6；四角/边缘存在透明像素；记录 `alpha_min/max`、完全透明与半透明像素数；尺寸符合
- **二级（视觉）**：主体外确实纯透明；没有棋盘格被画入；无红/绿/彩色光晕；无渐变底与地面阴影；边缘无脏边、无过度半透明
- **浅底 + 深底各看一次**（浅底是发现灰边的主验收背景）

### 6.4 几何验收（UI 专属，比通用流程多一条）

对生成的效果稿，用 PIL 做元素包围盒比对：

```text
基准 = R1_actual_1080x2160.png 的实测框（见 plan 文档 §一）
判定：每个元件的框偏移 ≤ 3 canvas 单位（= 3.4 真机 px）算通过
```

超差 → 判失败，**先换时间/路由重试，不要靠改 prompt 硬拽**。

## 七、拆件与导入规范

### 7.1 拆件（程序化，Pillow）

1. 按 §三 规格从效果稿裁出每件 → 落到 `Assets/Sprites/UI/Combat/`（新建目录）
2. 规整：对齐到规格画布、居中、补透明边、纯色件**去光晕与渐变**（阈值抠图或直接重绘纯色）
3. 机器验收：尺寸、Color Type、四角透明、主体 Alpha 分布；写一份 `hud_assets_check.json` 记录

### 7.2 导入设置（照现有 HUD 占位件，参数见 `Assets/Sprites/UI/hud_slot_diamond.png.meta`）

```text
Texture Type: Sprite (2D and UI)
Sprite Mode:  Single
Pixels Per Unit: 100
Alpha Is Transparency: ✔
Generate Mip Maps: ✘
Compression:  None 或 Normal（占位件用的是 Normal）
Filter Mode:  Point（像素化件）/ Bilinear（笔刷金属件，与 hub_v9 一致）
```

> 新目录 `Assets/Sprites/UI/Combat/` 要**新建 .meta**（Unity 会自动生成）。

### 7.3 接线（两条路径都要走）

| 目标 | 接法 |
|---|---|
| 血条三件 + 头像框 | `Assets/ScriptableObjects/Warrior/HeroHUDSkin_Zhangfei.asset`（`healthBottomSprite` / `healthFillSprite` / `healthFrameSprite` / `portraitSprite`） |
| 棱形三件 | prefab 槽位节点 `ButtonFrame` / `ButtonFace` / `CooldownDim` / `CooldownFill` 的 sprite + `FrontItemBar._skillFrame` |
| 暂停底框/符号 | 场景内 `Combat/Overlay/Pause/PauseLayer/PauseButton`（**只在场景里，不在 prefab**） |
| 等级球 | prefab `LevelOrb` 的 `OrbLiquid`（液面）+ 外框节点 |

**执行顺序（今天实测踩过的坑）**：**先改 prefab 模板，再改场景实例，最后保存场景**。
反过来的话，prefab 保存会把场景实例的改动冲掉（今天实测：血条宽度与棱形尺寸被回滚）。

工具：`Assets/Scripts/Editor/HeroHudLayoutTool.cs`（菜单 `三国杀戮 ▸ 战斗UI ▸ 应用新布局`），**幂等**，场景与 prefab 各跑一次。

### 11.11 事实更正：头像的三个精灵到底是什么（2026-10-30 复核）

用户质疑"头像和框是不是连体的"——复核结论（数据为准）：

| 精灵 | 尺寸 | 不透明像素 | 形状包围盒 | 中心 100×100 是否有内容 |
|---|---|---|---|---|
| `zhangfei_head.png`（= `portraitSprite`） | 400×400 | 93,022 | x 26..372 / y 14..378 | **10000/10000 全不透明** |
| `zhangfei_filler_base.png`（= `ultimateBaseSprite`） | 400×400 | 12,556 | **x 280..358 / y 128..298** | 0 |
| `zhangfei_filler_main.png`（= `ultimateFillSprite`） | 400×400 | 12,556 | **x 280..358 / y 128..298** | 0 |

**结论**
1. **头像与描金龙框确实是同一张图**（`zhangfei_head.png` 同时含金框与 Q 版脸，中心 100×100 全实心）。
   → 想换角色就必须**拆分**：新框（中间透明）+ 单独的角色件。
2. **能量条是另外两张图**，形状是**圆盘右侧的一条竖向渐变条**（x 280..358 / y 128..298），
   `head` 在那一列是透明的，所以**能量条现在其实可见**（就是实机截图里头像右上那条"像小刀"的红色竖条）。
   → ⚠️ **更正此前"能量环压在肖像底下看不见"的判断（那条判断是错的）**，它本来就是设计成露在圆盘外缘的。
3. 由此产生的新约束：新头像盘若做成**不透明整盘**，会**盖住这条能量条** → 能量读数消失。
   → 新方案必须二选一：
   - **拆三层**：新框（右侧留能量槽 + 中间透明）/ 剪影单独一件 / 能量底+能量填充（沿用现有两张，但要贴合新槽位）
   - **能量移出圆盘**：头像盘不透明 + 能量改成**盘外圈的一圈弧形刻度**（新件 `hud_portrait_energy_arc.png`，用 Fill 裁切）

### 11.20 防御动作位移：为什么「只加 -Z」不成立（2026-10-31）

**枪身轴一直在 XY 平面内**：`PlayerWeaponStance.PoseForAngle` 只绕 Z 轴转
（`dir = (cos a, sin a, 0)`），`parryStanceTipDegrees ≈ 42°` → 枪从握把 (-2.12,-2.74) 到枪尖 (+5.91,+4.48)，
**长度轴是 (8.03, 7.22) = 屏幕平面上斜 42°，z 全程 -2.42 不变**。

推论：
1. **-Z 不是「前刺」，是「把枪整体推离/拉近相机」**：枪身与 Z 轴垂直，平移 Z 不改变枪尖指向，
   在透视下只表现为**变大/变小 + 上下偏移**（相机俯视，-Z = 朝相机 = 屏幕下方）。
   它是"推近"的纵深，不是"刺出去"的纵深 —— 只给 -Z 会得到"枪突然怼到脸上"，而不是"迎敌"。
2. **本游戏的「前刺」方向是 +X**：命中判定按**列**走（5 列阵型），攻击横扫也是沿 X 扫过全列
   → 玩家面朝 +X，敌阵在 +X 侧 → 真正的「迎敌前压」必须走 **+X（枪身平面内）**。
3. **「整体偏右」的解与「前压」会互相抵消**：枪的中点在 x=+1.9，往左挪 -1.9 就回到玩家身上，
   但那样就把枪拉离敌阵了 → 需要**分两步**：先整体左移（构图），再沿枪身平面**斜向前压**（动作）。

**协调位移方案（三个可配参数 + 保留角度一致性）**
现有 `MoveTo(root, pose, dur)` 用同一条缓动 t 同时插值根节点与姿态 → **时间上天然同步**，
所以"配合"要靠**空间上互为反方向的锚点**：

| 参数 | 含义 | 初值建议 |
|---|---|---|
| `parryStanceDefendShiftX` (新) | 防御位整体左移，构图居中 | **-1.2** |
| `parryStanceDefendForwardX` (新) | 沿枪身平面(+X)斜向前压 | **+0.8** |
| `parryStanceDefendPushZ` (新) | 沿 -Z 推向相机（纵深） | **-0.8** |
| `parryStanceDefendAnchorDrop` (已有) | 下沉 | 保留 |

配套锚点：`_entryRoot` 放在防御位的**反方向**（x 更右、z 更深）→ 挥入变成"从右上后方斜插到左下前方"的弧线，
而不是原地转圈；`_exitRoot` 沿同一条斜线反方向退出 → 收枪不回头。

杆身中段必然还压在画面上 → **只要收枪不含 X/Y 平移，就无法"整杆出画后才销毁"**。
可选：
(a) 接受这一下"凭空消失"（不动 X/Y）；
(b) 收枪用**独立的一套位姿**（原来的 −100° + 下沉），只用于"破防被打飞"这种
    本来就该乱甩的场合，与"主动松手"区分开；
(c) 收枪允许 X/Y 平移（你已否掉）。
