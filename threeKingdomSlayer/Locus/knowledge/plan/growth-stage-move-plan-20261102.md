## 0. ⚠️ 本周工作性质：**不开新功能，只做解耦与配置**

> **本周绝大多数需求都是在已有功能的基础上做解耦和配置。**

| 类别 | 本周的做法 | 具体例子 |
|---|---|---|
| **配置** | 改资产，不改代码 | 关卡波次 / 倍率 / 里程碑 / 铜钱 / 技能进池的 `requiredTalentIds` / 节点清单 |
| **解耦** | 拆开现在耦合在一起的东西 | `HeroConfig.itemSlotCount` 一个字段管主动+道具 → 拆三个 |
| **接开关** | 给既有逻辑加一个「已解锁就生效」的读点 | 生命上限 / 铜钱获取 / 破阵 / 追击 / 运筹 / 不屈 / Slash 位移 |
| **改判定** | 改现有分支，不新开链路 | 满槽空候选分支 → 发钱；两处 `maxLevel` 判定 → 读「有效上限」 |

**明确不做**

| 不做 | 理由 |
|---|---|
| ❌ 新建存档体系 | 沿用现有分片模式（`TalentSaveSection` / `PropSaveSection` / `SupplySaveSection` 同构） |
| ❌ 新建 UI 框架 / Toast 系统 | 复用现有 `KillRewardUI.rewardPopup` / `UpgradeChoicePopup` / `ItemDiscardPopup` |
| ❌ 新建掉落系统 | 复用现有 `DropItemPoolConfig` + `EnemyManager.TryDropItem` + `BreakableProp` + `ExpGemManager` 范式 |
| ❌ 新建关卡工具链 | **已有完整工具链**（机器人 + 埋点 + 分析脚本 + 难度表脚本 + `WaveConfigEditor`）→ 见 `design/stage-configuration.md` §7 |
| ❌ 新建数值系统 / 事件总线 / 状态机 | 沿用现有 `StatModifier` / `BuffManager` / `UpgradeEffectManager` 注册表 |
| ❌ 引入 flag 机制 | `IsFlagUnlocked` 全项目零调用 → 本周**统一用 nodeId 解锁态**表达「已解锁」 |

**判据**：动手前先问「**这个能力是不是已经有了？**」
—— 项目里已经有一个完整的「配表 → 跑测 → 分析 → 调参」工具链、一套存档分片、一套 UI 组件、一套掉落通道。
**本周的活是把它们接起来、改对、拆干净，不是再造一套。**

## 1. 依赖顺序（**关键**）

```
招式衍生与拆分 ──► 关卡配置 ──► 天赋页面
 「玩家有哪些招式」   「每关考什么机制」  「哪些要解锁、放在哪」
```

**为什么是这个顺序**

| 依赖 | 原因 |
|---|---|
| 招式 → 关卡 | 关卡的敌人配方取决于「玩家有哪些手段可用」。招式没定，关卡难度无法倒推 |
| 关卡 → 天赋 | 关卡需求决定天赋树要解锁什么、解锁顺序怎么排。**先定关卡，才知道天赋页该放哪些节点** |
| 天赋 → 局内 | 天赋节点定稿后，才能配 `requiredTalentIds`（技能进池）与能力消费点 |

> **因此实现顺序建议倒过来**：先做「纯数据 / 纯配置」那批（不依赖任何前置），再回头按依赖链推进。

| **满槽金币补偿与铜钱经济失衡** | 补偿公式不当会让铜钱通胀/通缩 | 先按 `30 + 5 × 等级` 试，实机观察单局收入再调 |
| **等级上限开放后数值越界** | `GetTriggerInterval` 越界返回 -1 → **该被动直接不注册（失效）** | T-15 的公式里**必须夹 `availableRows`** |
| **1012 破盾概率** | 重攻击受击方向是 Random → ~1/3 概率破盾 | 已知设计张力（`gameplay-pillars.md` §4.2），本周不修 |
