# 字体优化问题（2026-10-20）

> 来源：包体实测（见 `plan/architecture-optimization-handoff-20261020.md` §6）。
> 状态：**已记录，本轮不实施**（用户要求先回结构线）。下面是需要决策的内容。

---

## 1. 现状（实测）

| 项 | 数值 |
|---|---|
| 包体里的字体资产 | `Assets/Fonts/方正粗黑宋简体 SDF.asset` = **35.4 MB**（另有源字体 `.ttf` 2.77MB、TMP 默认 `LiberationSans.ttf` 0.35MB） |
| 图集 | **4096 × 4096 静态**（`m_AtlasPopulationMode: 0`），内嵌 `image data` 16.7MB + mipmap + 字形表 |
| 字形数 | **7229** |
| 项目内出现的 CJK 字符 | **10215**（扫 595 个 .cs/.asset/.prefab/.unity/.json/.txt，含注释、日志、文件名 → 上限值） |
| 现有字体来源 | `Assets/Fonts/中日英语字库.txt`（42KB 字符清单） |

**推论**：项目里出现的汉字数（10215，上限口径）**大于**字体字形数（7229），
说明**现有字体已经覆盖不全**——部分中文现在可能就渲染为空白。
这是一个**独立的待确认缺陷**，与体积优化无关，建议优先查清。

---

## 2. 核心风险：静态子集化是单向门

如果按「当前用字」重新烘焙一个更小的静态图集：

- 以后任何新增文案（对话、天赋名、剧情、提示）用到子集外的字 → **TMP 静默跳过该字，界面显示空白**；
- 修复需要重新生成并提交字体资产，流程重、易漏；
- 汉字没有"拼写容错"，改一句话就可能引入新字。

**因此不建议在没有守门机制的前提下做「按当前用字」的静态子集化。**

---

## 3. 三个可选方案

| 方案 | 做法 | 以后加新字 | 体积 | 代价 / 前置 |
|---|---|---|---|---|
| **A. 保持现状** | 不动 | 不缺（只要新字不超出现有 7229 字形） | 35.4MB | 不省体积；**现有缺字问题仍在** |
| **B. 动态字体（推荐）** | 用 TMP Dynamic Font Asset，运行时按需生成图集 | 不会缺 | 初始只带基础字，通常 3-8MB | 需在微信小游戏真机验证：运行时图集生成的耗时/内存/首帧；也要确认 CJK 字库能被动态生成（部分字体许可/渲染器限制） |
| **C. 静态子集 + 缺字守门** | 烘焙一个大子集图集（覆盖当前所有文案），并加一个编辑器检查器 | 会缺，但**会被检查器拦下** | 20-30MB | 必须同时实现「文案缺字检查」：扫全项目文本（.cs 字符串 / .asset / .prefab / .unity 的 TMP 文本）比对字形表，缺字直接报错 |

> 若走 B，仍建议保留 C 的**检查器**：动态字体在部分平台也可能因为字形缺省/许可回退到方块，检查器能提前发现文案里出现的"字体根本不支持"的字。

---

## 4. 建议的下一步（按顺序）

1. **先查缺字**（与体积无关，优先级更高）：
   - 运行时普查：TMP 对缺字会打日志（`Glyph ... not found in font asset`），跑一遍全部流程收集；
   - 或静态普查：扫项目文本里的 CJK 字符集合，与 `方正粗黑宋简体 SDF.asset` 的字形表求差集 → 得到缺字清单。
   - 产出：一份「缺字清单」，先补齐（要么扩字体，要么改文案）。
2. 再决定体积方案：**优先 B（动态字体）**，其次 C（静态子集 + 检查器），A 是不作为。
3. 如果走 B/C，顺手把「文案字体覆盖检查」做成编辑器工具，纳入日常提交前检查。
