# 角色受击动画（视频→关键帧→抠图→部署）生产经验

来源：2026-10-03「持剑敌军正面受击动画」的完整实践。任务数据与每个版本的文件见 `memory/video-generation-case-log.md`；流程见 `skill/workflows/character-hit-animation-video-workflow.md`；图像 API 能力与路由指纹见 `skill/gpt-image-generation.md`。

## 1. 提示词必须分 5 层写（本次最大的教训）

| 层 | 内容 | 缺失后果 |
|---|---|---|
| ① 内容情景 | 这是什么片子、谁在做什么、为什么动、什么情绪 | 得到僵硬的平均解（本案例前两版就是这样） |
| ② 动作语义 | 什么力、从哪来、什么后果 | 模型只能猜动机，动作读不出来 |
| ③ 量化读点 | 关节与部位的具体变化（给模型落点） | 只会做整体缩放 |
| ④ 硬约束 | 画布/机位/尺寸红线/禁止项 | 漂移、超框、旋转 |
| ⑤ 节奏 | 受力窗口与回弹时间分配 | 冲击感不足 |

## 2. 正面锁定视角的三条铁律（都是实测踩过的）

- **"向后/后仰"在正面视角不可投影**：模型只能用**左右倾斜**表达后弓，所以必须显式禁止纵轴倾斜，改用**正面可见读点**：双肩上耸、脖子压缩、胸腔压扁、膝盖受力微屈、手臂惯性滞后、飘带/武器滞后。
- **不要写 `slightly wider` 这类"变宽"**：会被实现成整体放大，观感就是"充气"。必须写死"整体尺寸/体积/轮廓任何时刻不得大于 idle"。
- **表情的两难**：要求"表情是最清晰读点"→ 模型会重绘面部结构（身份漂移，本案例 v3 被否决）；要求"完全冻结面部"→ 表情零读点（v2/v4 的问题）。可行折中：**只允许受力瞬间眼睑收窄、眉毛下沉数帧**，面部几何/五官位置/颜色冻结。

## 3. 受击感主要来自节奏，不是静止姿势

静止关键图读不出"被动受力"是正常的；冲击感来自"受力只占 0.05–0.15s、回弹占其余时间"。所以关键图的职责应限定为**定姿势上限 + 保身份**，不要指望它给出冲击感。

## 4. 关键帧筛选要有客观依据

用「**相对 idle 的上半身变化量**」曲线定位真实关键帧。本案例实测：f12=16.0 → **f16=46.4（断崖 = 受力点）**、f16–36 为外扩相、f44–72 为收缩相（平台，等距采样会拿到重复帧）、f80=22.7（≈ idle）。

据此取 6 帧：**受击极值 / 后摇 / 回弹 3 帧 / idle 首帧**。第 6 帧用**已部署 idle 的首帧**（同源），切回待机不会跳姿势。播放 6×0.1s=0.6s；且"受力→后摇"在动画里只隔 0.1s，**快进慢出自动成立**。

## 5. 透明抠图路线：先探针，再决定（本次确立的 SOP）

1. **先发 1 次 GPT 语义去背探针**（`background=transparent` + `output_format=png`）。探针帧同时就是该帧的成品，成功不浪费。
2. 用指纹判断落到哪套后端（host + 回显字段 + token 记账）：支持透明的后端 → 其余帧全走 GPT；不支持的后端 → **立刻停手，不要连发**。
3. 不可用时改用**本地绿幕抠图**（前提：输入必须是绿幕）。该路线已由用户验收合格（见第 6 节）。

## 6. 本地绿幕抠图（实测要点）

> **2026-10-04 更新**：本节记录的「稳健 alpha + 反混合去污染 + 2px 环颜色替换」组合在「攻击帧」上仍产生可见绿边，根因是三处选错：alpha 被硬化成硬边+弱须、`g = max(r,b)` 中和把暖色描边变成「绿优势恰好 0」的橄榄色、全透明区未清零而留下被放大 20 倍的绿色噪声。**本地抠图以 `skill/workflows/local-green-screen-cutout.md` 为准**，本节仅保留历史记录与可复用的观察方法。

- **绿幕必须在输入阶段就存在**：角色本身 0% 偏绿，分离度极大；而把绿幕交给模型，它会把底换成**难抠的近白底**（白底键实测 1px 环亮度比 **2.31–2.61**、底抠不净、逐帧尺寸漂移 ±7%）。
- 验收合格的组合：**稳健 alpha + 反混合去污染**（用逐帧实测的绿幕色做 `C' = (C − (1−a)·BG) / a`）**+ 2px 环颜色替换**。
- 已知代价：2px 环替换会**同时淡化角色的深色描边**（1px 环/内部亮度比 0.61 → 0.88）；只做反混合则保留描边但会留淡绿（gEx1px −10 对基线 −46）。**"无绿边"与"保描边"在纯色键下互相排斥**，需按素材取舍。
- **验证指标不能只看亮度**：亮度比测不出绿边；整环 gEx 均值会被材质差异干扰。绿边必须专项量（环上像素 vs 内侧同材质邻域），并且**一律与已验收基线比**，不要用绝对值下判。

## 7. GPT 输出的几何会逐帧变化

- idle：可以逐帧按"各自源帧高度"归一化；
- **受击不行**：逐帧归一化会把"压缩"这个姿态本身抹掉 → 用「**单一全局缩放（各帧"源高÷输出高"的中位数）+ 逐帧只钉脚底锚点**」，并单独量化残余的逐帧尺寸差。

## 8. 接口可靠性：不要误判为"生图不稳定"

- **正常的不透明生图在任何后端都正常**：本案例 4 版关键姿势图全部一次成功，其中一次就落在所谓"坏" host 上（`r2.52image.xyz`）。
- 只有 `background=transparent` 会被部分后端忽略，而且那种情况**永远 HTTP 200、照常出图、不报错**，只是把透明换成自己画的近白底。
- 可用模型可免费查 `GET https://api.muskapis.com/v1/models`；`gpt-image-2.5-flare` 当前令牌无权限（HTTP 403），不要当候选。

## 9. 流程纪律（用户明确要求，必须遵守）

- 关键姿态参考图**先给用户目检验收**，再复述视频规格并取得确认，之后才能发起视频生成；不得以"参考图不上传、视频不依赖它"为由合并提交。
- 任何收费任务**不自行重试**；服务端 `failed` 且 `cost=0` 只证明未计费，不等于已获授权。
- 交付必须贴**完整路径**（含并排/对照图），不用省略号缩写。
- 提交任何生成任务前，把提示词的**中文对照版**贴在对话里给用户过目（提交仍用英文原文）。
