# 普通敌人并排比例参考图：成功经验

2026-11-08 四兵种并排图生成后，用户反馈“返图结果效果不错”。原图：`C:/Users/steam/Pictures/gptGen/enemy_proportion_lineup_v1/enemy_proportion_lineup_v1.png`；完整参数、四张输入哈希、提示词和状态见 `plan/enemy-commander-buff-unit-plan.md` §2.15。该图是比例研究参考，**不是可直接裁切入 Unity 的 Sprite，也不是四个兵种的最终造型定稿**。

## 可复用做法

- **先比较共同体型，再讨论具体兵种重做**：一次图像把重甲兵、山贼刀兵、旗手、弓手放在同一画面；用户可直接判断是否像同一类三国敌军，不必先重做已验收的角色或动画。
- **参考图职责明确**：1011 Idle 作为唯一共同体型 / 画风基准，另外三图仅提供各兵种的人物与装备方向；尤其 1013 和 1051 输入只是候选，不能当最终身份定稿。本次按四张 `image[]` 的顺序提交，并记录各自 SHA-256。
- **减少比较干扰**：四人同排、正面、脚底大体同基线、无明显透视远近；比较身体时不把旗杆、旗面、红缨、刀、弓、箭袋当作人体高度。同族不等于同脸、同装备、同剪影。
- **先看短壮结构再看装备细节**：比较头肩关系、胸腹 / 腰胯、腿、手脚和整体重心；外轮廓受重甲、头盔与握持姿态影响，不可把装备宽度直接等同于人体比例。
- **本次实测条件，不是效果保证**：`gpt-image-2.6-sunburst`、四张 `image[]`、`quality=max`、`input_fidelity=high`、1536×1024、PNG、n=1、未传 background；只提交一次。四图顺序 / 提示词 / 请求 / 响应 / 原图均已归档。仅一次成功，无法证明多图必优于单图，也不能把 `image_tokens=0` 推断成图片必然被忽略。
- **技术和美术结果分开核实**：实际 PNG 为 RGBA，但仍带半透明光晕；旗面出现装饰金边，刀兵头盔也与输入有所变化。用户认可整体效果，不代表逐项接受这些偏差或认可每个角色的最终造型。

后续制作单角色时可把这张图作为**人工并排复核体型**的参考，同时使用该兵种自己的身份参考；是否发起生成、修改现有角色、替换动画或接入 Unity，仍需按任务分别获得用户批准。

## 2026-11-08 裁切实验：为什么“不能直接裁切进游戏”有具体数字

从并排图裁出 1013 旗手并量测（脚本 `Tools/visual_brief/crop_lineup_1013.py`，产物见 `Enemy1013ArtSource/02_IdentityImages/1013_lineup_crop_reference_rgba.png` 等）后，“裁切参考图”不只是版权/口径问题，而是有可量化的硬伤：

- **人物本体是好的**：1013 人物身 476 px vs 1011 人物身 472 px = 1.008，同族成立。
- **旗杆总高 1.53×**（杆顶→脚底 720 px），设计目标 1.25×（§2.3）。
- **折算到游戏会溢出画布**：按 1012 idle 身 605 px 换算（k=1.271），总高 915 px → 杆顶 y=−18，1108² 精灵画布装不下。
- **旗宽会压邻列**：旗面 337 px → 折算 428 px，而列距 2.6 世界单位＝273 px，旗面跨 1.57 列。

另外自发多出：旗面金回纹边框、杆顶金属帽、旗布横向铺开、靛蓝头巾（均与 1013 定稿设定不符）。

**复用结论**：并排图可以裁出“身份参考”与“绿幕锚图”，但**不要**把这类裁切当角色定稿或游戏素材；旗手这类带高道具的角色，先用单图编辑把道具比例/装饰修正，再进视频管线。

## 2026-11-09 五人版 v2（加入新 1021）：方法增量与两条教训

成图 `C:/Users/steam/Pictures/gptGen/enemy_proportion_lineup_v2_1021/enemy_proportion_lineup_v2_1021.png`（1536×1024 RGBA，sha256 `6ccb9163…4282f`），记录见 `plan/enemy1021-art-production-handoff.md` §0.21。方法与产物都复用 v1 的做法（一次提交、五张 `image[]`、四张旧输入 + 一张新角色、脚本 `Tools/visual_brief/submit_enemy_proportion_lineup_v2_1021.py`、提示词外置在 `Tools/visual_brief/prompts/`）。

**量测工具与两条坑（脚本 `Tools/visual_brief/measure_lineup_figures.py`）**

- **背景光晕会桥接画面**：成图 alpha 分布为 0–16 占 75.6%、1–7 占 4.6%、主体在 129–253、**没有 255**。用低阈值（如 16）做连通域会把整行背景连成一块 → 阈值必须取 **128**，主体与背景才断开。
- **一个连通域 = 一个人，不能按 x 区间合并**：相邻角色的道具会 x 区间重叠（1011 的剑与 1012 的剑 x 重叠 10 px、1013 旗面与 1051 箭袋 x 重叠 48 px），按“x 区间相交就合并”会把 4 人粘成一组。正确做法是 **4 邻接 BFS 后每个连通域就是一个人**（邻居表必须是 `(1,0)/(-1,0)/(0,1)/(0,-1)`）。
- **头顶 ≠ 最高像素**：旗杆 / 弓尖 / 红缨都比头顶高。可用的头顶判定＝“以腿中心列 ±60px 为窗口，逐行往下找**窗口内连续可见段 ≥24px 且不越出窗口 40px** 的第一行”—— 红缨与旗面会因“越出窗口太多”被排除，等价于 v1 的“盔顶（不含红缨）→ 靴底”口径。

**同族量测结论（v2 与 v1 用同一算法，v1 作对照）**

**教训一：写“画面左 / 人物右手”模型会按人物左右理解，参考图的持盾侧不一定被继承。** v2 词里明写「shield on the LEFT side of the picture」，负面词也列了「shield on the right side」，并把持盾现行形象作为第 5 张参考图（其盾确在画面左），成图仍把盾画在**画面右**（人物左手）。含义：持盾类角色的**朝向性持握**（哪只手、哪一侧）不能只靠文字，要靠“只做这一处的单图编辑”或“先出单角色图再组图”，并**逐帧核对盾在哪一侧**；带手性/侧性的道具，负面词往往无效。

**教训一·解法（2026-11-09 已验证）：侧性问题用镜像解决，不靠模型听话。** 把成图里的角色裁出后**水平镜像**，盾就确定性地落到画面左、且落在人物右手上；再用这张镜像件当生图输入（“只换脸、其余不动”），盾侧就再也不会错。代价是脸被镜像了——所以镜像件只能当“身体/装备/持握侧”的参考，面相另用一张参考图单独给。

**盾侧判定法（`Tools/visual_brief/compose_identity_from_alpha.py`）：用「躯干带像素质心 相对 头部带像素质心」的左右判定。** 头部带（顶部 22%）只含头与头饰、不受侧向大道具影响；躯干带（35%~65%）会把竖盾/旗面算进来；盾在画面左 → 躯干质心在头质心左侧。**不能用“底部 25% 腿带”**——盾的下缘也在那一带，两边质心会被抵消（实测误判）。判定器必须用正反两个对照验证（未镜像件报 RIGHT、镜像件报 LEFT）再用于成图。

**原生透明成图的处理：gpt-image 偶尔直接给 RGBA 透明而不是绿幕**（本例 alpha=0 占 77.5%、四角 RGB≈(0,0,0,0)），`compose_identity_greenscreen.py` 走的是绿幕抠图，对透明图不适用。改用 `Tools/visual_brief/compose_identity_from_alpha.py`：按 alpha≥128 二值化 → 洪泛填封闭孔 → 缩放到主体高 696 → 贴 (474.5-w/2, 895-h) → 合成纯绿 (0,159,62)。与 1013 的“A-2 原生透明”属同一情形。

**教训二：把新角色塞进已有并排图组时，“参考图只提供 X、其余不继承”这条职责分离对**已定稿的四位**成立，但**对新品（1013）不成立**——1013 的旗面又自发长出金色回纹边框（v1 同一偏差），说明道具类角色的自发装饰偏差会跨轮复现，只能靠单图编辑逐项修，不能指望组图。

**教训三（2026-11-09）：单张 1024² 身份图会把画风“磨平”，成组的并排图才是画风与比例的最终闸门。** 1021 先出了单张身份图（面相对、盾侧对），但用户一眼看出**那张脸的渲染比并排图里其他几位更平滑、更绘制感**——因为单张渲染会把脸部细节画得更细、更平滑。解法是回到并排图：前四位输入**一个字节不动**，只把新角色的定稿身份图作为第 5 张输入，并加一段“图 5 提供的是设计、不是另一种画风”的硬约束＋一组针对性负面词（smoother rendering / airbrushed shading / glossy highlights / painterly rendering / finer detail on the fifth soldier）。v3 成图的第五位画风已与前四位一致。
→ 结论：**新兵种先出并排图定家族与画风，再出单张身份图做细节；单张图不能代表它在并排图里的样子。**

**盾侧判定的局限（重要）：质心法（躯干带质心 vs 头带质心）只对“大块实体道具”（盾、旗面）可靠，对剑/弓这类细杆会失真。** 实测：v2 上 1011 报 RIGHT、1012/1013/1051 报 LEFT；v3 上五人**全部**报 LEFT（同图内失去区分度）。因此盾侧必须**目视 + 两个独立信号交叉**：① 质心法；② 棕色连通块质心（把“木盾棕色”像素取最大连通块，看它的 x 质心偏哪边）。实测 v3 质心 x=72（中点 138）→ 画面左；同一方法对 v2 报 200（中点 135）→ 画面右，与目视一致。**不要只信单一判定器的单次输出。**

**教训四（2026-11-09）：图像接口对重请求不稳定时，先降请求体积，而不是反复重发同一个重请求。** 五图组图请求（~2.2 MB）连续两次失败：第 1 次读超时 901s 丢回执、第 2 次 HTTP 504 upstream_timeout（带服务端 request id）；而免费探针 `GET /v1/models` 200 / 0.6s 说明网关活着 → 失败在**上游处理重请求**这一环。图像接口是同步的，**没有 `/v1/images`、`/v1/tasks` 等取回端点，丢回执就等于丢产物**，无法 resume。改发**单图编辑**（538 KB）后 149.57s 正常完成。
→ 做法：① 提交前把读超时做成可配置（`--timeout`），重发时放宽；② 重请求连续失败两次就**换轻量路线**，别第三次重发同一个；③ 失败要向用户报 request id，方便找服务商查。

**教训五（2026-11-09）：单图编辑要拿“并排图裁切件”当底，而不是拿一张高分辨率单图当底——渲染语言会被底件带跑。** 1021 身份图 v1 的底件是低分辨率的并排图裁切（271×398 放大），结果脸被“磨平”；这次底件改成从 v3 组图裁出重贴的 1024² 底件（本身已是组图渲染语言），单图编辑后的画风与另外四位基本同源，残余差异只在脸部细腻度。→ 结论：**改单个角色时，先把目标角色从并排图里裁成 1024² 底件，再拿它当编辑输入**；比拿一张来历不明的单图当底更不容易画风漂移。

**教训六（2026-11-09）：表情强度有中间档，“太冷”与“浮夸”之间存在可用区间；而且调表情要从平静版底件重做，不要从夸张版往回收。** 1021 表情走了三档：v3 平静（用户判“不够凶狠”）→ 龇牙露齿版（用户判“用力过猛、太浮夸”）→ 压眉+收窄直视+闭嘴硬线（中间档）。中间档的写法要点：**眉压低略向内斜（浅纹不拧深褶）／眼收窄成锐利直视（不瞪大、不露眼白）／嘴必须闭上（双唇抿成硬线、嘴角略下压）／下颌颊肌绷紧**。项目里已验收的两档可作标尺：**1013 是闭嘴怒视、1012 是咧嘴（笑着的凶）**——瞇牙咆哮不属任何一档。
→ 负面词要**双向写**：前段列 `bared teeth / snarling / roaring / open mouth / bulging eyes / exaggerated expression` 治过猛，后段列 `calm / neutral / tired eyes / gentle gaze / smile` 防回落。
→ **关键操作**：从夸张版往回收会把夸张的残留留在底件里（瞇牙、瞪眼很难退干净）；**每次调档都从“平静/中性”那一版的底件重新做**，底件只负责身体/装备/盾侧/画风。

**教训九（2026-11-09）：替换视频路线在「同身体 + 同道具」时成立——动作载体与新形象一致，比“像不像”更关键。** 1021 attack 用替换法一次成功：旧 1021（1011 复制体）与新 1021 体型同源，且**母片里那面盾＝新形象的盾**（木胎＋深色铁包边铆钉、画面左、人物右手握），动作载体与新形象一致 → 文档担心的“形象随时间回退成参考片里的人”没有发生（97 帧头部带高饱和红占比 0.0002，母片 0.4041）。
→ 两个可复用前置动作：① **把身份图做成与母片构图/色键对齐的上传副本**（`Tools/visual_brief/prepare_replace_reference.py`：本体高/脚底/腿中心/底色逐项对齐母片实测值，只改底色不碰主体像素）；② **提示词用文档已验收的标准句逐字照用**，不扩写形象描述。

**教训十（2026-11-09）：查“角色回退”不能用普通红色像素占比。** 木盾的暖棕木纹会把判据污染（成片 0.32 vs 母片 0.38，看似没差别）。要用**高饱和红**（R−G>90 且 R−B>90）+ **头部带**（bbox 顶部 25–30%）——红缨/红围巾都在头部带，而木纹在躯干与盾面。这样成片 0.0002 vs 母片 0.4041 才是有效信号。

## 2026-11-09 Dead 组图轮：把“已部署动作帧”当动作母本（记录见 `plan/enemy-dead-group-reference-20261109.md` §10）

成图 `C:/Users/steam/Pictures/gptGen/enemy_dead_group_v1/enemy_dead_group_v1.png`（1536×1024，sha256 `ef3ae052…26a4`，一次提交、HTTP 200、125s；量测脚本 `Tools/visual_brief/measure_dead_group.py`）。路法：把工程内已部署的 `Enemy_1011_dead3.png` / `Enemy_1012_dead3.png` + 1013/1051 身份锚图共四张当输入，让四个角色画同一拍「腾空被打横」。

**路线有效**：四个身体确实读成同一拍动作（头脚方向、背弓弧线、屈腿、甩臂一致）；武器相对位置全部落在家族区间（脱手武器 dx −236…−317 / dy −110…−180，1051 的弓 +281/−135 在自己那一侧上方）；1013 的旗仍系在杆顶、杆旗整体脱手；1013/1051 的身份特征（络腮胡/头巾护额/米色交领袍/方扣皮带；发髻/蒙面布巾/怒视眉眼/木弓红缠带/三支白羽箭）都保住了。**姿态锚定从“靠文字重建”变成“有图可照”是有效的**。

**教训七（新增）：提示词里写“纯色绿幕背景 (RGB 0,159,62)”不保证得到绿幕。** 本次成图给的是**深棕黑渐变 + 人物周围发光**（角落均值 RGB 8,8,8）。后果：下游「裁切件 → 合成 1024² 绿底件」不能直接 chroma key，必须改**分割去背**（本轮用梯度泛洪分背景，`Tools/visual_brief/measure_dead_group.py` 里已实现），而且发光晕会在轮廓留黑边。→ 做法：把背景色当**出图后必检项**；若下游强依赖绿幕，考虑拆成两步（先出无背景姿态图 → 本地合成绿底），别指望模型听话。

**教训八（新增）：把“已部署动作帧”当动作母本时，继承的是姿态几何，不是画风与细节。** 四个参考里的两个是本项目的像素画，模型仍把全部四个重绘成平滑厚涂；基准角色 1011 还被改细节（丢了深色头盔）、被放大（身体块宽 482 vs 其余 340–389）、四肢张得更开（宽高比 1.805，越过“>1.6 = 平板”红线；原帧是 1.34）。→ 做法：动作母本帧只用于锚定姿态/比例区间，**画风与道具细节仍需在后续单图编辑阶段拿“已验收资产当底”重建**（同教训五）；且组图里的基准角色不可当“已验收事实”的替身——要判定同族必须回查原始帧。
