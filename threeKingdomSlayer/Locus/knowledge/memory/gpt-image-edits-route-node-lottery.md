# gpt-image edits 路由的“节点 lottery”行为（2026-10-22 实测）

## 结论

`POST https://api.muskapis.com/v1/images/edits` 前面挂着一批**阈值不同的网关节点**。请求落到哪个节点是随机的，落到的节点若在“首字节前静默期”内没等到上游结果，就直接断开连接，客户端表现为：

- `http.client.RemoteDisconnected`（服务端一个字节都不回），或
- `HTTP 504 upstream_timeout`（节点自己判超时，能拿到 error body 和 request id），或
- 客户端读超时（节点窗口很长，但作业本身更久）。

**能不能拿到图 = 抽到宽阈值节点 × 上游作业耗时。**

## 观测表（2026-10-22）

| 请求 | 输入体 | 耗时 | 结果 |
| --- | --- | --- | --- |
| P2 探针（合成小图 + 平凡词） | 1,238 B | 49.772s | 200 |
| 1011 v3 第 6 次（v2 图 + 改脸词） | 723,368 B | 135.355s | 200 |
| P1 探针（文生图，无输入） | — | 165.518s | 200 |
| P3 探针（合成噪声图 978KB） | 979,364 B | >305s | 客户端超时 |
| 1011 v4 第 2–6 次 | ~1,001,9xx B | 60.456 / 60.597 / 61.396 / 62.128 / 63.308s | 掉线 |
| 1011 v4 第 9 次（512px 输入） | 332,293 B | 71.295s | 掉线 |
| 1011 v4 第 7 次 | 1,001,967 B | 136.455s | 掉线 |
| 1011 v4 第 8 次 | 1,002,075 B | 148.171s | 504 upstream_timeout |
| 1011 v4 第 10 次 | 1,001,634 B | 66.901s | **200** |

观察到的断开阈值：**60.5 / 60.6 / 61.4 / 62.1 / 63.3 / 71.3 / 136.5 / 148.2 秒**，另有 >300s 的。

## 已被证伪的解释

- **不是 body 大小阈值。** 第 9 次 body 砍到 332KB（比失败组小 67%），照样被切在 71.3s。
- **不是提示词长度。** 压缩词、去 `input_fidelity`、加 `stream=true` 都不改变结果。
- **不是本机/网络/令牌/模型问题。** 同一台机器上 generations 路由 165.5s 成功、edits 路由 49.8s 成功；`GET /v1/models` 稳定 200。
- **不是 `stream=true` 能救的。** 网关在掐断前不吐任何 SSE 事件，没有流量可以保活连接。

## 实战要点

1. **要拿到图就得重发碰运气。** 1011 v4 连发时第 10 次（第 1 次就中）成功，用时 66.9s。
2. **命中一次很贵，所以命中那次要用最好的输入。** 用缩图/降质去赌唯一的好机会不划算——缩图不提高成功率（第 9 次实测），只损失身份保真。
3. **一次只发一个请求，顺序执行。** 并发连发会同时消耗多个作业窗口且互相挤占路由。
4. **记录要写全**：`.request.json`（字段组、词 SHA、输入 SHA、body 字节数）、`.status.json`（HTTP 状态、耗时、异常类型）。非 200 路径不写 `.response.json`，但 504 会写 error body。
5. **free 自检用 `GET /v1/models`**（不计费）；不要用付费探针试路由。
