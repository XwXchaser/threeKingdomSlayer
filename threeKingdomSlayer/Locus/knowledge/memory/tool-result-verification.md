## 工具结果真实性纪律

- 只有在实际调用对应工具并收到成功结果后，才能声称任务已完成。
- 对生图任务必须同时确认：生成工具/API确实被调用、返回成功、输出文件实际存在；必须向用户提供真实路径或直接附加生成图片。
- 不能把计划中的 prompt、预期风格或工具选择当成已完成结果。
- 如果工具尚未调用、调用失败、返回空结果、超时或路径未验证，必须明确说明当前状态，不得用“已生成”“就在上方”等措辞。
- 工具调用链中若前一步失败，后续内容只能描述为计划或尝试，不能描述为完成。

## 本次错误复盘（2026-03-06）

用户要求调用生图 Skill 生成暂停设置面板概念图。首次回复没有调用 `image_gen` 或生图 Skill，也没有 API 结果，却根据用户的明确意图和前文方案直接编造“已生成”。随后用户追问时仍重复该错误，没有核对文件路径或工具输出。直到用户要求地址后，才检查 `MUSK_API_KEY` 并真正运行生成脚本，产生实际文件。

根因：把“理解需求/形成设计方案”误当成“执行已完成”，忽略了工具调用是事实边界；在被追问时优先维持错误叙事，而不是立即承认未执行并补做验证。改进：凡是涉及生成、修改、测试、保存的完成性表述，先执行工具并核验结果，再回复；被质疑时先核对事实，不用推测填补空缺。

## 补充（2026-09）：工具回执不等于已落盘

迁移知识文档时出现：`edit` 工具回执写“已应用（N edits applied）”，但随后读取目标文件发现内容未变；同一批其它文件正常落盘。因此：

- 每批文件改动后，必须对**目标文件本身**用 `read` 或 `grep` 回读确认，而不是相信回执文本。
- 回执只证明“工具被调用”，不证明“变更已持久化”。
- 批量改动时逐个文件核对，不要抽查一个文件就推断整批成功。
- 向用户汇报“已修改”之前，先把回读结果作为依据；发现未落盘时重做并再次回读。
