## Current Pierce construction
- Runtime acceptance completed: all five selected columns now align, retract, release and fly along their formation-derived visual rays; the existing Pierce combat range and hit authority were confirmed unchanged.
- Pierce empty-cast input must use `InputManager.GetStabColumnFromScreenPosition`, which falls back to a fixed five-column screen mapping. The generic `GetColumnFromScreenPosition` only searches columns with a live front enemy and was the reason empty columns never reached `AttackSystem`, even though `ExecutePierce` itself returned success and supported empty travel.
- `PierceReleaseVisual` consumes the current `ChargeStabVisual` pose when available. On release, the same weapon first aligns from its current finger-driven pose to the selected column's visual flight axis, retracts 3 world units backward along that axis with length compression, briefly holds, then snaps back to the flight start and transfers ownership to `AttackWave`.
- The projectile axis no longer inherits the continuous finger tilt. `AttackSystem` derives a stable column visual ray from the selected column's row-0 formation X to the farthest effective row's formation X, while retaining the existing Pierce start Z and range-end Z. This keeps the release alignment, pullback and detached projectile on one axis and supports empty columns.
- Axial spin uses `Assets/Scripts/Effects/PierceAxialSpinVisual.cs`: two identical SpriteRenderer planes intersect at 90° under a shared spin pivot. Only the plane that is currently more camera-facing is shown, eliminating the translucent double-image from blended planes while still preventing edge-on disappearance.
- The release callback filters dead targets, then calls `AttackWave.CreatePierceFromVisual` with the existing release GameObject. No second spear prefab is instantiated: the same visual object is transferred to the projectile start, its render sorting is downgraded back to normal projectile order (`sortingOrder=0`), and `AttackWave` takes over detached flight/damage ownership.
- `Zhangfei_Pierce.asset`: damage 20, rangeRows 5, cooldown 3, actionDuration 0.50, prefab `Assets/Prefabs/Stab.prefab` (used as sprite/scale source, not instantiated on the normal handoff path).
- `AttackWave.SetupTravel` keeps the original straight-line Z-threshold hit authority and target/range selection. Only the detached Pierce visual movement uses the full formation-derived end position; reused Pierce visuals skip the normal scale-in reset, use a dedicated speed of 18 world units/s (shared projectiles remain 8), and use `Ease.OutCubic`.
- During flight the same `PierceAxialSpinVisual` accelerates from about 420°/s to 1800°/s. Its core directional blur is deliberately reduced to a 24px cap so the spear silhouette remains readable.
- `PierceAxialSpinVisual` retains only crossed-plane spear visibility, axial spin and weak 24px-capped core blur. The prior thin 9-block double-helix sleeve and repeated tail-ring implementation were removed because their continuous moving strips read as “noodles” rather than pixel VFX.
- Flight now adds `Assets/Scripts/Effects/PierceVortexVisual.cs`, based on accepted concept `C:/Users/steam/Pictures/gptGen/pierce_pixel_vortex_fragmented_concept_v3.png`. The first runtime attempt was rejected: it scaled the projectile root from 0.1 to roughly 1 and used overlapping thick-line/disc brush strokes, causing an 8–11× spear enlargement and a black-bordered orange blob.
- The vortex is generated by `PierceVortexVisual` from a hand-laid flame-claw layout, not a regular ring. Each of 4 frames defines 6–10 asymmetric curved claws (Bézier-bent polar paths with tapering width) plus sparse pixel sparks; each claw is stamped as layered discs (dark outline → red body → orange mid → gold highlight) to read as a pixel flame. Back and front layers are drawn to separate 128×128 point-filtered textures.
- A dedicated `Pierce_VortexAnchor` child is scaled/rotated so the spear root keeps its prefab scale 0.1; anchor visual scale stays ~4.5→5.3. Rendering is `VortexBack=-1`, spear=0, `VortexFront=1`, mounted perpendicular to the spear axis. A 30px center hole is force-cleared for the weapon channel. Afterimages consume the same frames via `GetBackFrame`/`GetFrontFrame` and use the anchor's world `lossyScale` (fixing the previous 8× oversized ghost). Preview sheets: `Library/Locus/tmp/pierce_vortex_front_sheet.png` / `pierce_vortex_back_sheet.png`.
- Pierce has a runtime aim indicator implemented by `Assets/Scripts/Effects/PierceAimIndicator.cs` and attached to `Assets/Scenes/Battle.scene/Player`. It stays hidden until charge progress reaches 1, then maps the pointer through the same `InputManager.GetPierceColumnFromScreenPosition` rule used by release. The indicator queries `AttackSystem.TryGetPierceIndicatorPath`, which returns the formation path (`start → row0 → row1... → target row`) plus the same 0.8-world-unit visual tail used by `TryGetPierceVisualPath`, so the arrow and preview now end at the detached projectile's fade-out endpoint while combat coverage remains `targetRow = effectiveRows - 1`. The 50%-alpha red rectangular body remains a ground-plane dynamic mesh, while the triangular head is a separate camera-plane mesh. A capped pool of independent `PierceAimIndicator_Pulse` instances reuses `PierceVortexVisual` without a spear, `AttackWave`, damage, hit feedback or afterimages. When the indicator appears or the player switches columns, pulses are immediately distributed across the entire path at the configured spatial spacing, then continue flowing to the endpoint in unscaled time; this prevents the initial visual gap caused by waiting for pulses to travel from the player. `pulseSpeed` and `pulseInterval` control flow speed and density.
- The real detached Pierce reuses this multi-vortex visual language through `Assets/Scripts/Effects/PierceVortexStreamVisual.cs`. `AttackWave.CreatePierceFromVisual` reads the indicator's pulse parameters and creates an independent, parentless stream from the real launch position to the real visual end position. Each emitted pulse is a spear-free `PierceVortexVisual` with no damage, hit feedback or afterimage. The stream derives its spawn interval from the preview's spatial vortex spacing, so real and preview vortices retain the same on-screen density. Tail pulses retain their normal scale through the first 70% of their travel, then smoothly expand radially to 2.25× while fading to zero by the visual endpoint, creating a terminal dissipating-vortex effect. `AttackWave` stops emission on range completion or destruction; already-emitted pulses finish their travel and dissipate before the stream self-destructs.
- Pierce target highlighting is driven by `PierceAimIndicator` only while its full-charge indicator is visible. It queries the same `ColumnManager.GetEnemiesInRange(column, effectiveRows)` rule as `ExecutePierce`, applies `Enemy.SetPierceHighlight(true)` to those live targets, and clears the exact prior target set on a column/path change, release, cancellation, death, disable, or destruction. `Enemy` renders this lowest-priority state as a red outline (behind QTE, SuperArmor, and C-frame outlines) plus a 22% warm-red shader lift through `_PierceHighlightStrength`; the lift is independent of wave tint and hit-flash material color, and is reset during pool initialization/recycling.

## Runtime ownership
- `PierceReleaseVisual`: player-side backload, axis correction, release callback and one-time ownership transfer.
- `PierceAxialSpinVisual`: reusable crossed-plane axial visibility and continuous spin state before and after transfer.
- `AttackWave.CreatePierceFromVisual`: attaches flight/damage ownership to the existing visual object without instantiating a duplicate.
- `AttackWave`: detached movement, target order, threshold hits, feedback, fade and destruction.
- `AttackSystem`: target/damage snapshot, charge-linked effects and composition of release visual with detached projectile.

## Constraints
- The projectile trajectory remains straight; “spiral” means rotation around the spear's own long axis, not a helical world path.
- The hand-held charge and detached projectile remain the same GameObject/visual hierarchy on the normal path; fallback instantiation is only for missing release visual resources.
- Do not apply motion blur during the hand-held charge phase. High-speed treatment belongs after ownership transfer.
- Do not merge the detached projectile lifetime back into action lock or attack speed scaling.
- Sweep should receive its own release visual rather than reuse Pierce's axial structure.
- Keep target snapshot, damage, row order and charge-shockwave logic authoritative in `AttackSystem`/`AttackWave`.
