# 工作回合纪律（防止「干到一半又停下」）

> 起因（2026-10-20）：同一个会话里，MiniMax 13 小时跑 612 步工具、17 条纯文本；换模型后 25 分钟内 11 个回合**每个都以文字收尾**，用户的主观感受是「任务永远做不完」。下面是据此定死的规则。

## 一、回合只允许三种收尾

1. **本阶段任务已完成**：代码/资产已落盘、已用匹配的手段验证、已 commit（必要时 push）。
2. **真正阻塞**：缺的信息会改变目标、范围或产物，且项目现状里找不到答案——这时用 `ask_user_question`，并把「我能自己继续的部分」先做完再问。
3. **用户明确叫停**。

除此之外**不允许**以文字收尾。即：只要任务没完成，一轮的最后一条输出必须是工具调用，而不是总结。

## 二、汇报放在工具之间，不放在回合末尾

- 需要让用户知道进度时，在两次工具调用之间写一两句，然后**继续调用工具**。
- 禁止出现「XX 已做完，要我现在跑验证吗？」「下一步可以 A 也可以 B，你说」这类收尾句。
- 能按项目现状判断的，直接判断并继续，把假设写在汇报里；不要为了形式上的确认而停。

## 三、Unity 状态切换要批处理

- **每次进/出 Play Mode 都会注入 `[Unity Editor Status Changed]`，立刻结束当前回合。** 频繁进出 = 频繁自断。
- 正确顺序：改代码 → 编译/热重载 → 静态检查（回读文件、看 diff）→ **进一次 Play Mode 把所有验证项一次性跑完** → 出来 → 提交。
- 不要「进去看一眼、出来改一点、再进去」。

## 四、工具调用纪律

- 不用 `request_editor_status` 断言状态（写死 `playing` 会在状态翻转时报错并结束回合）；只用幂等的 `unity_set_play_mode`。
- `bash` 里的 heredoc（`cat >> file <<'EOF'`）在本环境会写坏或写不进，改文件一律用 `edit`/`write`，改完回读确认。
- `unity_capture_viewport` 不能做 UI 像素验证（见 `memory/tool-result-verification.md`）。

## 五、死循环处理

- 同一个失败的调用/思路**不得连续重试超过 2 次**。
- 换证据来源：代码回读 → 运行时状态回读 → 日志 → 人眼。
- 仍不通就**隔离该点**（记进交接文档「未解决」），继续推进不受阻塞的部分，最后统一交代——不要卡在原地等救援。

## 六、todo 就是契约

- 多步骤任务必须维护 `todowrite`；同一时刻只有一个 `in_progress`。
- 没验证通过就不能标 `completed`；标 `completed` 时必须能说出验证手段。

## 七、自检清单（收尾前逐条过）

- [ ] 目标阶段的每一项都做完了吗？没做完 → 不许收尾。
- [ ] 改动落盘了吗（`read`/`git diff` 回读）？
- [ ] 验证跑了吗（编译通过 ≠ 行为正确）？
- [ ] 提交了吗？提交里有没有夹带别人未提交的改动（见 `plan/main-menu-hub-refactor-plan-20261020.md` §7.15）？
- [ ] 交接文档/记忆更新了吗（只写事实，不写「应该没问题」）？
